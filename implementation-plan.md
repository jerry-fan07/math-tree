# Knowledge Tree (Math): Swift Implementation Plan

**Date**: August 7, 2026
**Companion to**: [design.md](design.md) — the spec owns *what* is built; this plan owns *how and in what order*. Sections referenced as "§n" point into design.md.
**Toolchain (verified on the dev machine)**: Swift 6.3.3, Xcode 26.6 (build 17F113), arm64 macOS 26. CI pins the same Swift major version (exact Xcode build depends on what hosted runners carry).

---

## 0. Ground rules

1. **Platform: macOS-first, native.** SwiftUI app shell with a Metal-backed graph view. Rationale: Shifu observes desktop usage and graph exploration wants a large screen; iOS/multiplatform is a non-goal until after content scale-up (M5).
2. **One SwiftPM package, multiple targets.** `GraphCore` (library: model, validation, scoring), `ContentBuild` (executable: content compiler + layout), plus an Xcode app target that depends on `GraphCore`. Tests per target using the Swift Testing framework.
3. **Dependency rule: the app and `GraphCore` take zero third-party dependencies.** Tooling (`ContentBuild`) may use Yams for YAML parsing — the app only ever consumes compiled JSON via `Codable`.
4. **Persistence is deferred, by design** (§11.1). User state starts as an append-only JSONL evidence log folded in memory (§3.2 makes this replayable and sufficient); SQLite (e.g. GRDB) is the named swap-in when scale demands it. No database in early phases.
5. **Determinism throughout.** Seeded RNG in layout, replayable scoring folds, byte-stable build outputs. Same inputs → same map, same scores (§6.4's "the map always looks the same" depends on this).
6. **Every phase ends shippable**: the app builds, tests pass, and the phase's exit criterion is demonstrable. No phase begins until its dependency phases' exit criteria are met.
7. **Swift 6 strict concurrency** on; `GraphCore` types are `Sendable` value types.

## Phase 0 — Bare skeleton

**Goal**: an empty but real project: everything builds, tests run, CI is green.

**Tasks**
- `Package.swift` with `GraphCore` (empty stub type) + `GraphCoreTests` (one trivial test).
- Xcode app project `App/MathTree`: SwiftUI lifecycle, single window, "Knowledge Tree" placeholder view; depends on the local package. Pick the deployment target here (default: one major version behind current macOS unless a needed API forces newer).
- CI: GitHub Actions macOS runner running `swift build && swift test` plus an app build. One workflow, no cleverness.
- `.gitignore` (Xcode noise, build artifacts), initial commit structure.

**Deliverable**: launchable empty app + green CI.
**Exit criterion**: fresh clone → `swift test` passes and the app builds and launches to its placeholder window.

## Phase 1 — GraphCore: model + validation

**Goal**: the content data model (§2, §3.1) as Swift types, with the validator that enforces the spec's invariants.

**Tasks**
- `Codable`/`Sendable` types: `NodeKind`, `Prominence`, `Node`, `RelatesEdge`, plus a `KnowledgeGraph` container that builds derived indexes on load (children by parent, dependents by prerequisite, ancestor sets, reverse `relates`).
- Validator producing typed diagnostics (not just pass/fail), one check per §3.3 rule:
  - unique ids; id format (`branch.subbranch.slug`, lowercase-kebab)
  - no dangling references (`parent`, `also_under`, `requires`, `relates`)
  - `requires` acyclicity (DFS with cycle path reporting)
  - transitive-reduction: no `requires` edge whose target is already an ancestor via another path
  - exactly one primary parent; structural nodes carry no `statement`/`requires`
- Test fixtures: one clean mini-graph, plus one deliberately-broken fixture per rule.

**Deliverable**: `GraphCore` with full test coverage of the validator.
**Exit criterion**: every seeded violation is flagged with the offending ids in the diagnostic; the clean fixture passes; ancestor queries are O(answer), verified on a synthetic 10k-node chain without timeout.

## Phase 2 — Content pipeline + seed content

**Goal**: YAML in, validated `graph.json` + deterministic layout out; Appendix A exists as real content.

**Tasks**
- `ContentBuild` executable with subcommands:
  - `validate` — parse all `content/**.yaml` (Yams), run the Phase 1 validator, emit diagnostics with file/line context, non-zero exit on failure.
  - `build` — compile to a single `graph.json` (nodes, edges, derived indexes) consumed by the app.
  - `layout` — offline force-directed layout (Fruchterman–Reingold with Barnes–Hut approximation; `contains`-taxonomy gravity so branches cluster per §6.1), **seeded RNG**, coordinates written alongside `graph.json`.
- **Encode Appendix A as real YAML** in `content/` — it is simultaneously the seed content for the viewer and the integration fixture for the pipeline.
- Wire `validate` into CI; add an app build phase that runs `build` + `layout` and bundles the artifacts.

**Deliverable**: `swift run ContentBuild build` produces app-consumable artifacts from `content/`.
**Exit criterion**: Appendix A YAML validates and compiles; running `layout` twice on identical input yields byte-identical coordinates; CI fails on a deliberately broken content file.

## Phase 3 — Render spike (decision phase)

**Goal**: prove the renderer before building UI on it. This phase produces a *decision*, recorded in this file, not product code.

**Tasks**
- Synthetic generator: ~10k nodes / ~30k edges with taxonomy-like clustering.
- **Primary hypothesis**: Metal via `MTKView` in `NSViewRepresentable` — instanced quads for nodes, line primitives (or instanced segments) for edges, zoom/pan as a transform uniform, picking via CPU-side spatial hash (quadtree).
- **Fallback hypothesis**: SpriteKit, same scene. Build only if Metal misses criteria or costs explode.
- Measure honestly: frame time under continuous pan/zoom, first-paint time from cold launch, label rendering cost at overview LOD (§6.1's label rules affect this heavily — test with hub labels on).

**Deliverable**: throwaway spike target + a short decision note appended to this plan (chosen renderer, measured numbers, rejected option and why).
**Exit criterion (numeric, from §6.4)**: 60 fps sustained pan/zoom at 10k nodes / 30k edges; first paint < 1 s from launch; hit-testing under 1 ms. Whichever candidate meets these first, wins.

## Phase 4 — Viewer

**Goal**: the real graph view over real content — §6.1's overview experience, minus scores.

**Tasks**
- Replace the spike scene with production `GraphView` rendering `graph.json` + precomputed layout.
- LOD per §6.1: label visibility by `prominence` × zoom level; node size by prominence; `requires` vs `relates` visual distinction at mid zoom; progressive reveal on first load (hubs first).
- Interaction: smooth pan/zoom (trackpad + scroll), hover highlights direct prerequisites/dependents, click opens the node panel (title, kind badge, statement with math rendering, summary, prerequisite list as navigable links). Math rendering: evaluate `NSAttributedString`-based LaTeX-lite vs. bundling a math-layout approach during this phase — smallest thing that renders the seed content acceptably wins; revisit at content scale.
- Local relaxation only (optional polish): tiny neighborhood-level force nudges, never a full-graph simulation at runtime (§6.4).

**Deliverable**: browsable Appendix A subgraph in the app.
**Exit criterion**: all §6.1 zoom behaviors demonstrable on seed content; node panel shows every field of every node kind; cold launch to interactive < 1 s.

## Phase 5 — Scoring engine

**Goal**: §4 and §5.1 as a pure, replayable `GraphCore` module — no UI yet.

**Tasks**
- Evidence log: append-only JSONL per §3.2/§5.1 (`node/edge id, grade|confidence, source, timestamp`), stored in Application Support; reader/writer with corruption-tolerant parsing (skip bad lines, report).
- **FSRS**: first task is a survey — check for a maintained Swift FSRS implementation; if none is suitable, port the reference implementation. Either way, validate against test vectors taken from the FSRS reference repo, and record the algorithm version in the log header (§4.2 prescribes adopting the reference, not transcribing formulas).
- Scoring fold: evidence log → per-node/per-edge FSRS state; retrievability computed on read (§4.1) — no timers mutate state.
- Graph propagation (§4.3): explicit review on N emits damped implicit reviews (γᵈ, defaults γ = 0.5, D_max = 3, constants in one config struct) to `requires`-ancestors; implicit reviews never lower scores; explicitly-exercised nodes (§5.2) get full-strength implicit reviews. All propagation lands in the log with `source: implicit` — auditable, replayable.
- Frontier computation (§4.5): unlearned nodes whose prerequisites all exceed τ.

**Deliverable**: scoring module with the evidence log as its only input.
**Exit criterion**: FSRS matches reference test vectors; replaying the same log twice yields identical scores; propagation tests confirm damping, depth cap, and the never-lower rule; a property test confirms fold order-independence for same-timestamp events.

## Phase 6 — Score display + review loop

**Goal**: scores become visible and changeable — §4.5 in pixels.

**Tasks**
- Color ramp per §4.5: gray for unlearned, cold-to-warm retrievability gradient, frontier accent ring; edges blend endpoint colors, `relates` edges show their own score.
- Self-report flow ("I know this" with a confidence grade) writing `source: self-report` evidence — the placeholder review instrument until Phase 8's problems exist.
- Review surfacing: due-node list (FSRS scheduler read-out) in a sidebar; reviewing from it updates colors live.
- Node panel gains score, history sparkline, and next-due date.

**Deliverable**: the living map — knowledge state visible, reviewable, decaying.
**Exit criterion**: on a fixture user, frontier set matches hand-computed truth; a self-report on a deep node visibly boosts its ancestors (propagation observable in UI); relaunching the app reproduces identical colors (fold determinism through the UI path).

## Phase 7 — Focus mode

**Goal**: §6.2's learning view — the product's core loop becomes tangible.

**Tasks**
- Goal-node selection → `requires`-ancestor subgraph, topologically ordered left-to-right layout (computed on demand — small graphs, no precompute needed).
- Met prerequisites compressed (§6.2), unmet chain prominent; the ordered unmet set rendered as a syllabus list alongside the mini-graph (§5.4).
- Animated zoom-out/zoom-in transition between overview and focus (continuity of place, §6.2); breadcrumb back.

**Deliverable**: "what do I need to learn to get to X" answered visually.
**Exit criterion**: for fixture users with varying knowledge states, the syllabus order is a valid topological order and omits exactly the met prerequisites; transition runs at 60 fps.

## Phase 8 — Assessment

**Goal**: problems replace self-report as the evidence instrument (§5.2–§5.4).

**Tasks**
- Problem schema (`problems/`): statement, answer/rubric, `targets: [node id]`, `exercises: [node id]`; validated against the graph (no dangling ids) by `ContentBuild validate`.
- Grading flow: answering emits full-grade evidence for targets, full-strength implicit evidence for exercised nodes (§5.2).
- Adaptive placement (§5.3): claimed-frontier seeding, DAG probing (pass ⇒ raise ancestor priors, fail ⇒ probe prerequisites), low-confidence inferred evidence with faster decay, resumable sessions.
- Failure diagnosis (§5.4): on a miss, present the prerequisite chain for gap localization; evidence lands on the localized node only.
- Author a problem bank for the M2 single-variable-calculus content (parallel track, same review bar as content).

**Deliverable**: placement + problem-driven review over real content.
**Exit criterion**: on a seeded persona ("knows calc through derivatives"), placement converges to the expected knowledge boundary within a bounded number of probes; a failed FTC problem localizes to the seeded gap.

## Phase 9 — Content scale-up

**Goal**: M5 — the full undergraduate curriculum (§1), subbranch by subbranch via the §7.1 process.

**Tasks**
- Author per-subbranch YAML batches (LLM-drafted, human-reviewed per §7.1 — the review bar is the product).
- Cross-branch `requires` integration passes after each branch lands.
- Performance regression gate: re-run Phase 3 measurements at real scale each time the graph doubles; layout quality tuning (cluster separation, hub spacing) as the map grows.
- Tooling as needed: authoring lint hints (likely-atomicity-violation heuristics), diff-aware validation output for review.

**Deliverable**: the complete map.
**Exit criterion**: full corpus validates clean; viewer holds Phase 3's numeric criteria at full scale; spot-check reviews (sampled per branch) find no invariant violations.

## Phase 10 — Shifu evidence intake

**Goal**: M6 — the §8.2 contract, implemented as a boundary, not an integration.

**Tasks**
- Freeze the evidence-event JSON schema (versioned) as the public contract.
- Local intake mechanism — decide at implementation time between an XPC service, a local socket, or a watched drop-directory; criteria: Shifu runs on the same machine, events are small and append-only. Whatever transport, events land in the same evidence log with `source: shifu`.
- Confidence-weighted handling per §5.1/§5.3 (observed-usage evidence is inferred-tier: low confidence, faster decay until confirmed by a direct test).
- A `shifu-sim` CLI subcommand on `ContentBuild` that replays a canned event stream — the integration test double, so this phase completes without Shifu itself.

**Deliverable**: documented, tested intake contract.
**Exit criterion**: simulated Shifu events flow through to visible score changes; malformed and unknown-id events are rejected with diagnostics, never crash, never corrupt the log.

## Decision log

Decisions made during implementation that deviate from, or resolve an option left open by, the plan above. Newest phase last.

### Phase 0

**D0.1 — No Xcode project; the app is a SwiftPM executable plus a bundling script.**
The plan's repo layout named an Xcode project at `App/MathTree`. That path is kept, but as a SwiftPM `executableTarget` (`path: "App/MathTree"`), with `Scripts/bundle-app.sh` assembling `build/MathTree.app` (binary + minimal `Info.plist` + ad-hoc signature) around the built binary. Rationale: no project generator is installed (`xcodegen`/`tuist` absent), and a hand-written `project.pbxproj` is fragile and would force CI onto `xcodebuild`. CI stays `swift build && swift test` plus one script. A bare SwiftPM SwiftUI executable needs `NSApplication.shared.setActivationPolicy(.regular)` in the app delegate or no window fronts — done in `MathTreeApp.swift`. Reversible: if an Xcode project is ever needed (entitlements, notarization, App Store), the sources move unchanged.

**D0.2 — Deployment target macOS 15.**
Per the plan's default ("one major version behind current macOS"): dev machine runs macOS 26, so `.macOS(.v15)`. Revisit only if a Phase 3/4 Metal or SwiftUI API forces newer.

**D0.3 — Metal shaders are compiled at runtime, not by SwiftPM.**
Probed empirically before Phase 3 depended on it: a `.metal` file placed in a SwiftPM Swift target is **silently ignored** — no `default.metallib` is produced, `Bundle.module` isn't even generated, and `makeDefaultLibrary()` returns nil. So shaders ship as a text resource and are compiled at launch with `MTLDevice.makeLibrary(source:options:)` (tens of milliseconds, comfortably inside §6.4's sub-second first-paint budget). If that cost ever matters, the escape hatch is a `xcrun metal`/`metallib` step in `bundle-app.sh`.

**D0.4 — App launch is verified by a `--smoke-test` flag, not by screen capture.**
`MathTree --smoke-test` prints the visible windows and exits non-zero if there are none. Screen recording is not available to CI runners or to headless tooling, and this makes "launches to its placeholder window" an actual assertion. Current output: `window: "Knowledge Tree" 1280x800`.

**D0.5 — CI is delivered but not demonstrated green.**
The repo has no remote and none was created (that is the user's call), so `.github/workflows/ci.yml` has never run on GitHub. Every step in it was run locally and passes. Phase 0's "CI is green" is therefore *pending a remote*, not met.

### Phase 1

**D1.1 — Ancestor sets are a query, not an index.**
Phase 1's task list names "ancestor sets" among the indexes `KnowledgeGraph` builds on load. Built eagerly they are O(n²): the phase's own exit criterion is a 10,000-node `requires` chain, where materialized ancestor sets are ~50M entries. So the cheap indexes are eager (children by parent, dependents by prerequisite, reverse `relates`) and `requiresAncestors(of:)` / `requiresDescendants(of:)` are per-query traversals doing O(answer) work. Measured on the 10k chain: construction 66 ms, deepest-node ancestor query 9 ms returning exactly 9,999 ids, depth-bounded (`D_max = 3`) query 13 µs. The depth-bounded variant is what Phase 5's propagation will actually use.

**D1.2 — No `missing-statement` rule.**
`statement` is optional in the §3.1 schema and design.md never states its presence as an invariant, so a rule would false-positive on legitimately terse content. Structural nodes *are* checked for the inverse (they must carry no `statement`/`requires`/`relates`).

### Phase 2

**D2.1 — Hand-rolled argument parsing.**
Ground rule 3 sanctions Yams for tooling and nothing else. Three subcommands and five flags do not justify pulling in swift-argument-parser, so `ContentBuild` parses `CommandLine.arguments` directly.

**D2.2 — `GraphCore.contentFormatVersion` became `ContentFormat.version`.**
A `public enum GraphCore` inside module `GraphCore` shadows the module name, which makes `GraphCore.Node` unresolvable from any target that also imports Yams — and Yams exports its own `Node`. Renaming the enum was the fix; qualifying at every use site would have spread the problem.

**D2.3 — Node ids `ftc-1`/`ftc-2` → `ftc-part-1`/`ftc-part-2`.**
design.md contradicts itself: §3.1's normative schema example uses `analysis.svc.ftc-part-2`, Appendix A's table uses `an.svc.ftc-2`. Ids are permanent (§3.1) so this had to be settled before content scale-up. The normative section wins; Appendix A self-describes as "Illustrative only".

**D2.4 — What makes the build byte-stable.**
Four things, each of which independently breaks the Phase 2 exit criterion if dropped: content files are walked in sorted path order; `JSONEncoder` uses `.sortedKeys` (`dependents` and `children` are dictionaries, and Swift's dictionary iteration order varies between runs); layout iterates a sorted node order and uses a seeded SplitMix64 rather than `SystemRandomNumberGenerator`, which cannot be seeded; coordinates are rounded to 4 decimals on the way out. No artifact carries a timestamp or build id. Verified: three consecutive `build` + `layout` runs produce identical SHA-1s.

**D2.5 — Layout tuning.**
Fruchterman–Reingold, Barnes–Hut repulsion (θ = 0.9), fixed 600 iterations (a convergence tolerance would make output depend on floating-point noise). Springs are weighted `contains` 2.0 > `requires` 1.0 > `relates` 0.4, and each node is pulled toward its root branch's centroid. Measured on a synthetic 10k-node / 30k-edge taxonomy-shaped graph: inter/intra-cluster distance ratio 2.9 with cluster gravity off, 5.9 at the default 0.05, 7.9 at 0.12. 0.05 is the default because higher values collapse branches into unreadable blobs. Layout of 10k nodes takes ~5 s — offline, so it doesn't touch §6.4's first-paint budget.
*Known limitation, deferred to Phase 9*: initial positions come from an index-order spiral, so inserting one node reshuffles every position downstream of it. That is fine while content is a fixed seed set, but it fights §6.4's "spatial memory becomes navigation" once M2 authoring starts adding nodes incrementally — the fix is to seed positions from a hash of the node id rather than its index, and it should land before the map is something a user has memorized.

**D2.7 — `Package.resolved` is tracked.**
Pinned rather than ignored: this package produces executables, and leaving Yams to re-resolve on each CI run would let the build drift to a newer 5.x than the one it was tested against, which cuts against ground rule 5.

**D2.6 — The CI gate is tested, not assumed.**
`Scripts/check-broken-content.sh` seeds six distinct violations (dangling requires, cycle, transitive-redundant edge, duplicate id, malformed id, structural node with prerequisites) one at a time into a copy of `content/` and asserts a non-zero exit for each, then confirms clean content still passes. GraphCore's tests cover the *rules*; this covers the *wiring*, which is what silently rots — a swallowed exit code makes CI green on broken content.

### Phase 3

**Hardware for every number below**: Apple M4 (10-core GPU, unified memory), macOS 26.5.1, Swift 6.3.3, `swift build -c release`. Real `MTKView` in a SwiftUI window; drawable **2880×1736 px** (1440×868 pt at backing scale 2), 120 Hz display. Synthetic graph: 10,000 nodes / 30,167 edges (9,985 `contains`, 18,182 `requires` of which 14.6 % cross-branch per §2.4, 2,000 `relates`), prominence 0/1/2 = 7215/2172/478, positioned by the Phase 2 layout. All figures were reproduced on a second independent run before being recorded here.

**D3.1 — Metal wins; SpriteKit was never built.**
All three numeric criteria pass at 10k/30k with large margins, so the plan's own rule ("build the fallback only if Metal misses criteria or costs explode") says stop. Overview zoom with hub labels on, measured **offscreen with frames strictly serialised** — no pipelining, no compositor, the pessimistic number: **1.69 ms GPU mean, 2.1–2.2 ms GPU p99, 2.94 ms whole-frame p99** against a 16.67 ms budget. Triple-buffered throughput 814 fps at p99; in a real window it sustained a flat 120 fps (the display is the limiter — `currentDrawable` blocked 8.13 ms of every 8.33 ms frame). CPU encode p99 **0.20 ms**: three draw calls, zero per-frame uploads. Mid zoom is the same story (2.8–2.9 ms GPU p99). **Criterion 1: PASS, ~5.7× headroom.**
Also rejected: `.line` primitives for edges (no width control, no Retina antialiasing — instanced quads cost the same and look right); a quadtree for picking (see D3.3); CPU frustum culling (GPU-clipped off-screen instances beat the bookkeeping at every scale tested, including 100k).

**D3.2 — First paint ~0.21 s; the cost that scales is JSON decode, not the GPU.**
Measured from the kernel's process start (`sysctl` `kinfo_proc`) to the first *completed* drawable: **median ≈ 212 ms over five launches (range 204–221)**. Breakdown at 10k: AppKit/dyld/SwiftUI bring-up 164–182 ms, `graph.json` decode 28 ms (3.7 MB), instance-buffer build 2.7 ms, label atlas 5.0 ms raster + 1.1 ms upload, id→index resolve 1.6 ms, shader compile 0.5 ms, GPU buffers 0.07 ms. **Criterion 3: PASS, ~4.5× margin.** Three things Phase 4 should carry:
- **Metal caches the runtime-compiled shader on its source text.** A genuine cold compile costs **66 ms** (first paint 271 ms) — still passing, which confirms D0.3 was a safe call. Only a user's first-ever launch pays it.
- **First paint tracks decode and nothing else meaningfully**: 28 / 95 / 339 ms of decode at 10k / 30k / 100k nodes → 204 / 294 / 729 ms total. Still inside 1 s at 100k, but decode is then 47 % of it. If content nears 30k nodes, replace `graph.json` with a binary or mmap-able artifact. This is the number Phase 9's "re-measure each time the graph doubles" gate should watch.
- The **first launch of a freshly linked binary** costs 1.9–4.3 s (code-signature validation and page-in), against ~46 ms of our own work. State the criterion as steady-state launch and keep `bundle-app.sh`'s ad-hoc signing.

**D3.3 — Hit testing is a non-issue: 125 ns worst case against a 1 ms budget.**
CPU uniform grid in CSR form (counting sort), cell size = the layout's ideal edge length; build 0.16 ms for 10k nodes. Over 32,768 randomised picks: **47 ns mean / 61 ns p99** at overview zoom, 54 ns in the densest cluster, **worst single call 125 ns** (375 ns at 100k). **Criterion 2: PASS, ~8,000× margin.** A quadtree would be over-engineering; the grid stays.

**D3.4 — Frame architecture Phase 4 inherits: three static buffers, one uniform, three draw calls, zero per-frame uploads.**
- Nodes: instanced quad (`triangleStrip`, 4 verts × N instances), circle from an SDF in the fragment shader, premultiplied blend. `NodeInstance` = 16 B (`float2 pos; float radiusPx; uint rgba8`).
- Edges: instanced quad expanded perpendicular in screen space in the vertex shader, endpoint colours interpolated, alpha falloff across the width. `EdgeInstance` = 24 B. Guard `normalize()` against zero-length edges.
- Labels: `LabelInstance` = 48 B sampling an R8 `texture2d_array` atlas.
- Pan/zoom is **one 40-byte uniform** (`setVertexBytes`), never a buffer rebuild. Radii are in points, multiplied by the backing scale once.
- **LOD is an instance-count prefix, not a rebuild.** Sort instances by tier once at load (branch → subbranch → prominence 2 → 1 → 0); a zoom level is then `drawPrimitives(instanceCount: prefix)`. This is why CPU encode stays flat at 0.13 ms while the scene changes.

**D3.5 — Label cost is real but small, and the binding constraint is atlas *memory*, not draw time.**
Marginal cost is **0.19–0.31 µs per visible label**, roughly flat in graph size (it scales with label count × label area, not node count). §6.1's designed overview LOD — branch + subbranch hubs + prominence-2, i.e. 613 labels at 10k — costs **+0.14 ms per frame, under 1 % of the budget.** The label risk Phase 3 flagged did not materialise. What bites is the atlas: 613 labels = 2 pages = 8 MB / 5 ms to rasterise, but 10,000 labels = 22 pages = **88 MB** / 69 ms and 30,000 = **276 MB**. So: rasterise the overview tier eagerly at load (it is on the first-paint path and costs 5 ms), build higher tiers lazily per zoom band, release pages on zoom-out. Core Text into a grayscale `CGContext`, shelf-packed, uploaded once — no text engine, no per-frame glyph work.

**D3.6 — Edges are the only thing that scales badly; the cliff is ~170–340k edges.**
By ablation at overview zoom (serialised offscreen): edges are **~92 % of the frame** at both 10k and 100k, scale linearly at **≈46–49 ns/edge**, and are nearly insensitive to width (an 8× width range moves the total 1.27×) — so the cost is per-primitive screen extent (tile binning for long thin diagonals), not fill rate, not draw calls. Nodes cost 0.51 ms at 10k and only 0.84 ms at 100k. Extrapolated, the serialised budget is reached near **340k edges**, with a 2× safety margin at **170k**. §7's own estimate (5,000–15,000 nodes ⇒ ~15–45k edges) sits comfortably inside, so no edge LOD is needed for the planned corpus. Scale points measured: 10k/30k → 2.94 ms p99, 814 fps; 30k/90k → 6.05 ms p99, 300 fps; 100k/302k → 19.77 ms p99, 69 fps (**fails 60 fps**). When it grows, cull **edges**, not nodes — and note that at 100k the overview is a saturated white blob, so **legibility fails before frame rate does**; the answer there is content-driven LOD (draw `contains` plus high-prominence `requires` only at overview), not a rendering trick.

**D3.7 — Two measurement traps, recorded so Phase 4 doesn't re-learn them.**
- **`CAMetalLayer.displaySyncEnabled = false` does not uncap an on-screen `MTKView`.** The property reads back `false`, yet `currentDrawable` still blocks ~8.13 ms at 120 Hz. Worse, on-screen `gpuEndTime − gpuStartTime` is inflated ~3× by drawable scheduling (5.1 ms on screen vs 1.55 ms offscreen for an identical frame). **Profile offscreen**; treat the on-screen run only as "does it hold the display's cadence".
- **Never put `--flag value` pairs on an AppKit command line.** AppKit parses leftover `-key value` tokens into `NSUserDefaults`, and `--first-paint --graph x.json` made SwiftUI never call `makeNSView` — the window silently never existed and the process hung. A single *trailing* boolean flag survives, which is why D0.4's `--smoke-test` works. Anything richer must use environment variables or `--key=value`.

**Deliverable**: a throwaway SwiftPM spike (synthetic generator, Metal renderer, Core Text atlas, spatial hash, self-measuring harness), deliberately **not** retained in the repo — Phase 3's product is this decision, and Phase 4 writes the real `GraphView` from D3.4/D3.5 rather than growing the spike.

### Phase 4

**D4.1 — Edges are three draw calls, not one; the invariant that mattered was zero per-frame uploads.**
D3.4 handed down "three static buffers, one uniform, three draw calls". The buffers and the uniform are exactly that, but edges are split into `contains` / `requires` / `relates` and drawn as three ranges, each carrying its own width, alpha, dash duty and arrowhead strength through a 40-byte `DrawParams` (`setVertexBytes`). §6.1's mid-zoom clause — `requires` distinguishable from `relates` — needs per-class style, and the 24-byte `EdgeInstance` has no bits left for it. A typical frame is 5 draw calls (3 edge classes + nodes + labels), 7 while hovering. What the spike actually measured (0.13–0.20 ms CPU encode) was the *absence of buffer rebuilds*, not the draw count; two extra `setVertexBytes` are noise against that.

**D4.2 — `NodeInstance` keeps its 16 bytes but spends 4 on `half2` instead of `float`.**
D3.4's layout was `float2 pos; float radiusPx; uint rgba8`. Radius became `half2 radii` = (radius at overview, radius at full detail), mixed in the vertex shader by a `bandT` uniform. Same 16 bytes, but LOD *morphs* continuously instead of snapping at band boundaries — which is what makes zooming read as one continuous map rather than three. Half precision on a value in 1.9–17.0 points is well under a pixel. The same trick gives each label a `fadeStart` so tiers emerge at their own zoom.

**D4.3 — LOD is a hard prefix *and* a cosmetic fade; only the prefix is load-bearing.**
Instances are tier-sorted once at load (branch → subbranch → prominence 2 → 1 → 0) and a zoom level is `drawPrimitives(instanceCount: prefix)`, exactly as D3.4 specified. The per-tier alpha fade happens *within* the drawn prefix, so it never costs an instance that would otherwise be skipped. Measured on seed content, label prefix **9 / 19 / 27** across the three bands — §6.1's rule asserted, not claimed. The node prefix is 27 at every band and stays flat until a tier's radius falls below 0.75 px; the mechanism is present so scaling is a constant change, not a rewrite.

**D4.4 — Arrowheads ride mid-edge (62 % along), not at the target endpoint.**
An endpoint arrowhead must be backed off by the target's radius, which varies with the zoom band and is not carried per edge instance — no room in 24 bytes and no cheap vertex-shader lookup. A marker at a fixed fraction of the edge needs only the endpoints, stays legible at every zoom, and reads as flow rather than as decoration on the node. Arrow alpha ramps 0 → 0.85 over `bandT` 0.18–0.38, so arrowheads are absent at overview and present from mid onward; `relates` gets the complementary treatment (dash duty 1.0 → 0.5 over the same ramp).

**D4.5 — Zoom bands are multiples of fit-to-view, not absolute scale.**
`bandT = clamp(log₂(scale / fitScale) / 3, 0, 1)`; overview below 1.6× fit, mid 1.6–4.0×, detail above 4.0×. Anchoring to fit means "overview" means *the whole map* whether the corpus is 27 nodes or 10,000 — a threshold in points-per-world-unit would silently become wrong the first time content doubled. Probe and snapshot cameras use ratios 1.0 / 2.5 / 4.5 with anchors derived from content (busiest subbranch, best-connected content node), so "at mid zoom" is a reproducible camera rather than a hard-coded id.

**D4.6 — The label atlas is eager for one tier and lazy for the rest, per D3.5.**
Branch + subbranch + prominence-2 rasterise in the renderer's initialiser (2.4 ms, 9 labels, 1 page on seed content) because they sit on the first-paint path. Prominence-1 and -0 rasterise the first time `bandT` crosses their fade threshold. The label buffer is allocated once at full capacity and written as tiers arrive — still a static buffer, growing at band crossings, never per frame. D3.5's memory numbers are what force this: 613 labels is 8 MB but 30,000 would be 276 MB.

**D4.7 — Demonstrability: `--probe` is a trailing boolean; everything richer is an environment variable.**
D3.7's trap is respected literally. `--probe` renders the real scene in the real window, prints a JSON report from the first *completed* drawable, and exits; a 12 s watchdog exits 2 with a readable message rather than hanging — the exact failure D3.7 recorded. Snapshots are entirely env-driven (`MATHTREE_SNAPSHOT`, `_ZOOM`, `_SIZE`, `_REVEAL`, `_HOVER`) and render **offscreen**, so they need no window server. Because input cannot be driven headlessly, the probe also asserts the two calculations that would otherwise be unverifiable claims: projecting every node to screen and picking it back (**27/27**) and cursor-anchored zoom drift (**0.000000 pt**).

**D4.8 — Colour carries taxonomy, not score.**
Phase 4 is "minus scores", so §4.5's retrievability ramp is absent entirely. Hue is assigned per branch by sorted branch id (curated palette first, golden angle beyond it) so colours survive rebuilds, with saturation and value stepped by tier. This makes `contains` clustering legible now and leaves §4.5 a clean slot in Phase 6: the ramp replaces the tier tone, the hue assignment stays.

**D4.9 — LaTeX-lite wins the math-rendering evaluation; no layout engine is bundled.**
The plan's rule was "smallest thing that renders the seed content acceptably wins", and the corpus does not need a box model: the only genuinely two-dimensional constructs across 22 statements are super/subscripts and fractions. Super/subscripts are baseline offset plus a 0.72ⁿ size ramp — exactly `NSAttributedString`'s expressive power; fractions linearise to `(a)/(b)` with parentheses dropped around a single atom, so the hardest case, `$f'(c) = \dfrac{f(b) - f(a)}{b - a}$`, sets as `f′(c) = (f(b) - f(a))/(b - a)`. Cost: ~970 lines, zero dependencies.
The parser is pure Foundation and yields **two read-outs of one parse**: styled runs for display, and a linearised plain text where a script group becomes Unicode (`∫ₐᵇ`, `∑ᵢ₌₁ⁿ`, `xᵢ₋₁`) when every character has a script form. The second read-out exists precisely because the panel cannot be screenshotted — it is how the corpus was reviewed and what the self-check asserts against (clean over all 76 title/statement/summary fields).
**Degradation is the design constraint, not an afterthought**: content will always outrun the macro table. An unknown macro renders its braced argument if it has one and its own name upright if not; an unterminated `$` renders the remainder as math. Never a dropped tail, never a raw backslash — verified by 8,000 fuzzed renders over truncated and mutated real statements. The honest revisit trigger is not content volume but the first authored statement needing *stacked* notation (matrices, continued fractions), at which point a layout pass, not a bigger table, is the fix.

**D4.10 — The panel was verified by rendering it, and that found a real defect.**
Compile-clean plus `#Preview`s was the ceiling the panel work could reach on its own: the panel is a SwiftUI overlay, so it never appears in the renderer's Metal snapshots, and screen capture is unavailable here. It was therefore rendered offscreen (`NSHostingView` + `cacheDisplay` into a bitmap; `ImageRenderer` was tried first and leaves `ScrollView` content **blank**, which would have produced a false pass) for three nodes chosen to cover the kinds: `ftc-part-2` (heavy math, the only `relates` edge), `analysis` (structural), `def-riemann-integral` (the combining-mark worst case). Result: every §3.1 field renders, structural nodes correctly omit Statement/Requires/Related and gain Contains, and the math sets correctly — **except that the combining low line does not render on `∫`**. `\overline` joins (`∫̅ₐᵇ` is visibly barred), `\underline` does not, so `def-riemann-integral`'s lower integral displays as a plain `∫`. The statement stays unambiguous because `sup_P L(f,P)` and `inf_P U(f,P)` sit right beside it, but the notation is degraded. Fixing it needs a real overline/underline rule drawn as geometry rather than a combining character — which is the layout pass D4.9 defers, so it waits for the same trigger.

**D4.11 — Known gaps, stated rather than glossed.**
Three §6.1 behaviours are implemented but not *demonstrable* on 27 nodes: node-LOD culling never engages (nothing falls below 0.75 px), edge LOD does not exist by design (D3.6 put the cliff at ~170k edges against §7's ~45k estimate), and "branches read as galaxies" has only two branches to work with. Live trackpad feel is unverified — headless input is impossible here, so the probe asserts the underlying math instead. Local relaxation (listed as optional Phase 4 polish) is not built. The label atlas rasterises for `NSScreen.main` only, so a window dragged to a different-scale display resamples rather than re-rasterises.

### Phase 5

**D5.1 — Survey outcome: port, don't depend.**
Maintained Swift FSRS implementations do exist (`open-spaced-repetition/swift-fsrs`, MIT, FSRS-5 and -6). Ground rule 3 nonetheless rules them out: `GraphCore` takes **zero** third-party dependencies. So FSRS-6 is ported from the reference implementation, `open-spaced-repetition/py-fsrs` @ `8add2d3`. That commit is recorded in `FSRSVersion.oracle`, in the evidence-log header, and in the vector fixture — a test fails if they drift apart. swift-fsrs was also rejected as a *test* oracle: it may not carry py-fsrs's recent same-day-Hard stability fix, so a mismatch would be noise rather than signal. One oracle, pinned.

**D5.2 — Only the memory model is ported; the card-state machine is not.**
The reference's Learning/Review/Relearning states with their learning steps are Anki scheduling UX. Verified before porting that all three states perform **byte-identical** memory updates — the three-way branch is on elapsed time (`< 1 day` → short-term stability, else the recall/forget path), not on card state. So the port covers initial state, difficulty update, stability update, retrievability, and the interval read-out, and nothing is lost. Confirmed empirically: driving the reference with `learning_steps=()` reproduces its own published `test_memo_state` vector (S = 53.626903 vs 53.62691, D = 6.357487 vs 6.3574867). Interval fuzzing is omitted outright — ground rule 5 requires determinism.

**D5.3 — Vectors were generated before the port was written.**
FSRS publishes no standalone test-vector artifact; its reference test suite is the closest thing, and it contains only two memory-state assertions. `Scripts/gen-fsrs-vectors.py` therefore drives the reference to produce **420 unit vectors** (per-function grids over initial stability/difficulty, retrievability, next difficulty, short-term stability, next stability across 320 D×S×R×grade combinations, and intervals) plus **42 review sequences / 248 steps**, asserting every *intermediate* state rather than only the last. Generating the fixture first matters: a fixture written after the port would encode the port's bugs. The two published reference vectors are additionally asserted directly. The tests were mutation-checked — perturbing one weight from 1.8722 to 1.8723 fails four of them, so they can actually fail.

**D5.4 — Whole-day truncation in the update path, continuous decay for display.**
The reference computes elapsed time as `(t2 - t1).days`, floored to whole days, in both the update path and its retrievability call. The port matches that exactly in `review(_:grade:at:)`; anything else silently diverges from the oracle by amounts too small to notice and too large to ignore. But §4.1 says the score "decays continuously", and a colour that only moved at midnight would visibly step — so `retrievability(of:at:)`, the display read-out, uses fractional days. Two functions, deliberately, with the divergence documented at both sites.

**D5.5 — Propagation is write-time expansion; the fold never generates events.**
§4.3's implicit reviews must land in the log with `source: implicit` so they are auditable and replayable. That forces the split: appending an explicit review also appends the implicit events it induces (`Propagation.expanded`), and the fold only ever *applies* what it is given. Had the fold derived propagation while the log also stored it, every replay would double-count. Refitting γ later is then a filter, not a rewrite: drop `source: implicit`, re-expand the explicit events under new constants. Each implicit event carries its own `origin`, `depth` and `weight`, so a replay reproduces the original damping even after γ changes.
Mechanism: `S_new = max(S_old, S_old + γᵈ·(S_explicit(g) − S_old))`. Difficulty is untouched — §4.3 speaks only of stability, and difficulty is a property of the material rather than of this retrieval. Failures propagate nothing (§4.3 makes a failed review a retest flag, not a penalty); `propagateOnFailure` exists to test the never-lower clamp, which is otherwise vacuous. Depth is shortest-path — `requiresAncestorsByDepth` is breadth-first, verified before relying on it, so a diamond damps by its short route.

**D5.6 — An implicit review resets the decay clock, and that is a guess.**
Exercising a prerequisite *is* a retrieval of it, so its retrievability should recover; damping then expresses that the strengthening is weaker than a direct review, not that the retrieval never happened. But this is exactly the kind of constant §11.3 flags as unfounded, so it is a flag (`implicitReviewsResetDecayClock`) in `ScoringConfig` beside γ, `D_max` and τ rather than an assumption baked into the maths.

**D5.7 — A real ordering bug, found by a test asserting documented intent.**
FSRS updates do not commute, so the fold sorts events by a total order over their content before applying — order-independence comes from sorting, not from the maths. The first implementation ordered same-instant events by `source.rawValue`, which puts `"implicit"` before `"test"` alphabetically: the exact opposite of the ordering the code's own comment claimed. A node both reviewed directly and boosted at the same instant would have had the boost applied first, letting the explicit review compound an inflated stability. Fixed with an explicit `foldRank` (direct evidence anchors, derived boosts land on top). Worth recording because the bug was invisible to every test that only checked determinism — two wrong-but-consistent orderings are still deterministic.

**D5.8 — Confidence-only evidence is reported, not guessed.**
§5.1 allows an event to carry `grade` *or* `confidence`; the fold consumes grades. Inferred-tier handling (low confidence, faster decay, §5.3) is Phase 8/10 work, so a confidence-only event is surfaced as a fold defect rather than silently interpreted as some default grade. Unknown ids get the same treatment — which is also Phase 10's "malformed and unknown-id events are rejected with diagnostics, never crash, never corrupt the log" criterion, satisfied early and for free.

### Phase 6

**D6.1 — §4.5's ramp overrides D4.8's guess, and the hubs had to be desaturated for it.**
D4.8 predicted "the ramp replaces the tier tone, the hue assignment stays". Half of that survives. §4.5 prescribes an *absolute* ramp — grey when unlearned, deep blue → teal → green by retrievability — which cannot coexist with a per-branch hue on the same node, and §6.1 says colour encodes score *throughout*. So the split is by **learnability**: content nodes take §4.5's ramp, structural hubs keep their branch hue because they are not learnable (§2.1) and are the map's navigational skeleton. Rendering it exposed the consequence D4.8 did not anticipate: Foundations' branch hue is 152°, inside the ramp's own arc, so the hub read as a mastered node. Structural saturation therefore drops from 0.34/0.48 to 0.12/0.18 — hubs are near-white with a cast of their branch, and the galaxies still read through size, halo and the `contains` filaments, which keep full hue. The rule that came out of it: **nothing outside the ramp may sit inside the ramp's arc**, which is also why the frontier accent is warm gold.

**D6.2 — Edges: `contains` keeps taxonomy, `requires` blends endpoint scores, `relates` shows its own.**
§6.1 asks for blended endpoint colours and §4.4 gives `relates` edges their own FSRS state. `contains` is left on the taxonomy palette because its parent is structural and has no score — colouring it by one endpoint would be inventing data. `requires` keeps Phase 4's directional weights (0.55 at the prerequisite, 1.0 at the dependent) so it still reads as flow rather than a symmetric link, with the endpoints' score colours substituted. A `relates` edge with state paints both ends its own colour; without state it falls back to the endpoint blend, so an unexercised connection still reads as belonging to two nodes. Edge colours are dimmed 14 % against their nodes — §6.1 wants hairlines, and a well-known neighbourhood at full edge brightness becomes a blob.

**D6.3 — Self-report is affirmative only; there is no "I don't know this".**
Three confidence levels (Shaky / Solid / Fluent) mapping to Hard / Good / Easy. `again` is deliberately unreachable, and the reason is structural rather than stylistic: the frontier is defined by the *absence* of FSRS state (§4.5), so a self-reported failure would write state onto an unlearned node and silently delete it from "what you could learn next" — the opposite of what the user meant. §4.3 already says a failure is a retest flag, not a penalty; giving that its own semantics is Phase 8's job, alongside the problems that can actually localise a failure (§5.4). The rule lives in `SelfReportConfidence` and is asserted, not merely enforced by which buttons were drawn.

**D6.4 — The sidebar's due list is the scheduler, not the threshold, and the two are allowed to disagree.**
`ReviewQueue` reads FSRS's own `nextDue`; `Frontier.due` (Phase 5) asks the different question of whether retrievability has fallen past τ. FSRS schedules against its desired retention (0.90) and τ is 0.85, so the lists differ at the margin by construction — the scheduler decides *when to review*, τ decides *what counts as mastered for the frontier*. Both are kept. Only nodes are queued: `relates` edges carry state (§4.4), but an edge review means a problem exercised the connection, and self-reporting one would be evidence about a question nobody was asked.

**D6.5 — Every review is an append plus a full refold, never an incremental update.**
`ScoreStore.record` appends `Propagation.expanded(...)` and then re-reads and re-folds the whole log. Two reasons, one correctness and one evidential. Correctness: appended events can share a timestamp with existing ones, and the fold's total order only holds over the whole log (D5.7) — folding a batch onto current state would apply it in arrival order. Evidential: it makes the UI path *literally* the replay path, so "relaunching reproduces identical colours" and "replaying the log reproduces identical scores" stop being two claims. It costs one fold of a small file per button press, which is invisible at any corpus this design admits.

**D6.6 — Verification needed an injectable clock; without it the exit criterion is unassertable.**
Retrievability decays continuously against the wall clock (§4.1), so two launches over the same log *should* differ, and "identical colours" has no meaning until the clock is pinned. `MATHTREE_NOW` pins it; `MATHTREE_EVIDENCE_LOG` redirects the log; both are environment variables, per D3.7. Runs with `--probe`, `--smoke-test`, `MATHTREE_SNAPSHOT` or `MATHTREE_PANEL_SHOT` are **read-only** by construction — a verification run that appended would corrupt the developer's own history *and* stop being repeatable, which are the two things it exists to protect. Confirmed: after the whole verification pass, `~/Library/Application Support/MathTree/` still does not exist.
`Scripts/check-score-determinism.sh` launches the app twice over `fixtures/fixture-user.jsonl` and diffs the probe's score read-out — **27/27 nodes byte-identical**, comparing the rgba8 words read back out of the buffer the GPU drew from, not a recomputation. It then launches once over the one-review-later log and *requires a difference*, because a check that cannot fail proves nothing: 8 nodes repaint, frontier 4 → 5, learned 10 → 16. It is deliberately not in CI — it needs a Metal device, and the existing smoke test passes even when the renderer fails to come up, so a green CI run would not mean what this script means.

**D6.7 — Colour changes rewrite words inside existing buffers; the decay tick is a minute.**
D3.4's invariant is zero *per-frame* uploads, and neither a review nor a decay tick is per-frame — this is the pattern the hover highlight has used since Phase 4. `applyScores` rewrites node `rgba`, both scored edge classes, and a frontier-ring buffer sized for every node (a fresh user's frontier can legitimately be most of the map). The tick is 60 s, far finer than a ramp whose units are days, and it is suppressed when the clock is pinned. The trap worth recording: the `MTKView` pauses itself once the reveal settles, so a colour write is invisible until something asks for a frame — every recompute ends in `requestRedraw`.

**D6.8 — The fixture user is code; the JSONL is its golden output.**
Propagation is a write-time expansion (D5.5), so a log must *contain* the implicit events it induced — and hand-typing those would encode a human's arithmetic instead of `Propagation`'s. So `FixtureUser` authors only the eleven explicit reviews and derives the log, with `fixtures/*.jsonl` a committed golden copy (`MATHTREE_UPDATE_FIXTURES=1 swift test` regenerates; a test fails when they drift). They are committed rather than generated on demand because the app reads them directly, and a fixture the app can only obtain by running a test is not a fixture the app can be launched against.
The fixture earns its keep by being *borderline*: the MVT sits at 0.838 against τ = 0.85, so the threshold is load-bearing rather than decorative — that single node is why `zero-deriv-const` is off the frontier, and a test lowers τ to 0.80 to show it is the only thing moving.

**D6.9 — The overlays were rendered offscreen again, and again it found real defects.**
D4.10's method (`NSHostingView` + `cacheDisplay`; `ImageRenderer` blanks `ScrollView` content and would pass falsely) was reused for the score section and the sidebar, and caught two things that compiled and previewed fine: positioned subviews inside the sparkline's `GeometryReader` claimed layout space past their frame, leaving a visible dead gap under the chart, and edge markers clipped at the bounds. Both are gone — the sparkline is now one `Canvas` with an inset plot. Unlike Phase 4, the harness is **kept** (`PanelShot`, `DEBUG`-only, env-gated): the overlays will keep growing through Phases 7 and 8, and it is ~120 lines against the alternative of re-deriving the method each time.
It also closes the one link no snapshot can reach. Input cannot be driven headlessly, so the button press itself is unverifiable — but `MATHTREE_PANEL_SHOT_REPORT` drives `ScoreStore.record` over a *copy* of the fixture log, and the resulting file is **byte-identical to `fixtures/fixture-user-reviewed.jsonl`**. The write path therefore produces exactly the log the tests assert on, and the colour it produced (`#8C919E57` → `#49F27CFF`, frontier 4 → 5) is the one the snapshot shows.

**D6.10 — What the first launch looks like, stated rather than softened.**
With no evidence log the map is entirely grey except the structural skeleton and **one** gold ring, on `foundations.real.sup-inf` — the single root of the `requires` DAG. That is §4.5 working exactly as specified, and it reads as an instruction ("start here") rather than as an empty state, so the ramp was not pre-emptively softened to make a fresh install look busier. It does mean the first-run map carries almost no colour information; §5.3's placement probe is the designed answer, and it is Phase 8 work.

**D6.11 — Known gaps.**
`relates` edges can never show their own score yet: nothing writes edge evidence, because §4.4 says an edge review happens when a *problem* exercises the connection (Phase 8) — the render path is built and exercised by construction, but unreachable from the UI. Live trackpad interaction with the sidebar is unverified for the same reason all Phase 4 input was. The decay tick repaints on a timer rather than on a display link, so a node crossing a ramp boundary can lag by up to a minute — invisible at day-scale stability, wrong if τ ever becomes an animation. The panel's history sparkline replays one node's events on demand; that is O(log) per panel open and will want a cache long before it wants a different algorithm.

### Phase 7

**D7.1 — The syllabus and its layout live in GraphCore, because the app target has no tests.**
`FocusPlan` owns everything the exit criterion quantifies over: the unmet set, its order, the met-boundary compression, and the left-to-right column/row layout. The app contributes point spacing, colour and interaction — nothing assertable. The load-bearing choice inside it: layering is longest-path over the **full** ancestor subgraph, met nodes included, and the syllabus is the unmet set sorted by (layer, id). Any directed path strictly increases the layer, so this stays a valid topological order even when one unmet node precedes another *only through met intermediates* — the case a layering over the pruned unmet subgraph silently gets wrong, and the case `unmetPrecedenceSurvivesAMetIntermediate` pins. "Met" is checked against `Frontier`'s exact notion (state exists ∧ retrievability strictly > τ, one shared clock) so the gold rings and the syllabus can never disagree at the margin — where the fixture deliberately parks the MVT (0.838 vs τ = 0.85, D6.8), which is why the fixture syllabus *containing* the MVT is the single strongest assertion in the phase.

**D7.2 — "Compressed" means: visible at the boundary, elided behind it, counted always.**
§6.2 says met prerequisites are compressed; the reading implemented is structural, not just visual. A met ancestor is displayed only where the unmet chain actually touches it — as a direct prerequisite of an unmet node or the goal — drawn small and dim *in its true topological position*; every met node behind that boundary is elided entirely, with the count shown ("4 earlier prerequisites you already know are not shown") so compression reads as compression rather than absence. Consequence, observed on the reviewed fixture: elision can disconnect the drawn subgraph (the decayed Riemann-sum fragment floats apart from the goal's own boundary), because the paths joining the fragments run entirely through elided met nodes. It reads acceptably — fragments stay row-aligned and the syllabus carries the order — so met-path routing is deferred until real content produces an illegible case.

**D7.3 — The transition is a camera flight under an overlay fade; 60 fps is asserted structurally, per D4.11.**
Entering focus flies the camera to the goal at detail zoom while the overlay fades in; leaving flies back to the camera captured at entry (captured once — refocusing deeper must not overwrite where "Full map" returns to). The flight interpolates scale in log space (zoom is perceptually multiplicative), eases with smoothstep, snaps to the exact target at completion, and is cancelled by any user gesture. Frame rate cannot be measured headlessly, so the claim is structural: the flight writes the same 40-byte uniform a settled frame writes — zero buffer traffic, so a transition frame costs what D3/D6 already measured — and the probe reports the on-demand plan cost (0.1–0.2 ms on seed content) and the flight's target camera. The trap re-learned: the `MTKView` pauses itself when settled, so `flyCamera` must kick `requestRedraw` or the flight never takes off.

**D7.4 — The probe's focus goal is the deepest-ancestry content node, not the detail anchor.**
D4.5's convention (content-derived, deterministic cameras) is kept but the derivation changed: the detail anchor is the *best-connected* node, and its plan over the fixture user is trivially met — it would demonstrate nothing. The node with the most transitive prerequisites (`u-sub` on seed content) is the most demanding goal the corpus offers, which is the case focus mode exists for. The probe re-derives both exit-criterion clauses independently of `FocusPlan`'s internals — transitive-precedence topological validity and omits-exactly-met recomputed straight from FSRS state — and reported true for all three fixture states (empty log, fixture user, reviewed).

**D7.5 — The focus overlay was rendered offscreen, and for the third time the method found real defects.**
D4.10/D6.9's harness (`NSHostingView` + `cacheDisplay`; PanelShot now also writes `focus-*.png`) caught two things that compiled and previewed clean: adjacent-column labels colliding ("Continuous on [a,b] ⇒ integrable" ran into "FTC, Part I" — layered layouts put nodes on the same row in adjacent columns *constantly*), and long titles overflowing their column. Fixed by wrapping labels within their column's width and alternating them above/below the node by column parity. The write path is closed the same way Phase 6 closed it: `MATHTREE_PANEL_SHOT_REPORT` drives the real `ScoreStore.record` over a copy of the fixture log, still byte-identical to `fixtures/fixture-user-reviewed.jsonl`, and the after-report focus shot shows the syllabus collapse 7 → 1 — §4.3's propagation expressed as compression.

**D7.6 — Known gaps.**
Elision-induced fragmenting (D7.2) awaits an illegible real case. A plan recompute after a review snaps the canvas rather than animating node motion — the enter/leave transitions are animated, in-place compression is not, and making it so means diffing plans, which nothing yet justifies. Escape is owner-priority (panel first, then focus) and navigation keys are suspended while focus covers the map; live trackpad feel of the flight is unverified for the reason every phase has recorded — input cannot be driven headlessly. The syllabus list reuses `NodeReferenceRow`, so an entry's subtitle says "ready to learn" only for frontier nodes; a mid-syllabus entry whose prerequisites are unmet correctly reads "unlearned", which is §4.5 speaking, not a bug.

## Risks (top three, with mitigations already embedded above)

1. **Renderer misses the numbers** — contained by Phase 3 being a cheap decision spike with a named fallback, before any UI is built on it.
2. **FSRS port correctness** — contained by reference test vectors and the versioned, replayable log (a wrong algorithm can be fixed and replayed, §3.2).
3. **Content authoring is the long pole** — contained by making it a parallel track from Phase 2 onward and gating only Phase 8 on it; engineering phases never wait on content beyond the seed subgraph.
