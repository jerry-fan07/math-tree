# Knowledge Tree (Math): Swift Implementation Plan

**Date**: August 7, 2026
**Companion to**: [design.md](design.md) — the spec owns *what* is built; this plan owns *how and in what order*. Sections referenced as "§n" point into design.md.
**Toolchain (verified on the dev machine)**: Swift 6.3.3, Xcode 26.6 (build 17F113), arm64 macOS 26. CI pins the same Swift major version (exact Xcode build depends on what hosted runners carry).

---

## 0. Ground rules

1. **Platform: macOS-first, native.** SwiftUI app shell with a Metal-backed graph view. Rationale: Shifu observes desktop usage and graph exploration wants a large screen; iOS/multiplatform is a non-goal until after content scale-up (M5).
2. **One SwiftPM package, multiple targets.** `GraphCore` (library: model, validation, scoring), `ContentBuild` (executable: content compiler + layout), plus an Xcode app target that depends on `GraphCore`. Tests per target using the Swift Testing framework.
3. **Dependency rule: the app and `GraphCore` take zero third-party dependencies.** Tooling (`ContentBuild`) may use Yams for YAML parsing — the app only ever consumes compiled JSON via `Codable`.
4. **Persistence is deferred, by design** (§11.1). User state starts as an append-only JSONL evidence log folded in memory (§3.2 makes this replayable and sufficient); SQLite (e.g. GRDB) is the named swap-in when scale demands it. No database in early phases.
5. **Determinism throughout.** Seeded RNG in layout, replayable scoring folds, byte-stable build outputs. Same inputs → same map, same scores (§6.4's "the map always looks the same" depends on this).
6. **Every phase ends shippable**: the app builds, tests pass, and the phase's exit criterion is demonstrable. No phase begins until its dependency phases' exit criteria are met.
7. **Swift 6 strict concurrency** on; `GraphCore` types are `Sendable` value types.

## Phase 1 — GraphCore: model + validation

**Goal**: the content data model (§2, §3.1) as Swift types, with the validator that enforces the spec's invariants.

**Tasks**
- `Codable`/`Sendable` types: `NodeKind`, `Prominence`, `Node`, `RelatesEdge`, plus a `KnowledgeGraph` container that builds derived indexes on load (children by parent, dependents by prerequisite, ancestor sets, reverse `relates`).
- Validator producing typed diagnostics (not just pass/fail), one check per §3.3 rule:
  - unique ids; id format (`branch.subbranch.slug`, lowercase-kebab)
  - no dangling references (`parent`, `also_under`, `requires`, `relates`)
  - `requires` acyclicity (DFS with cycle path reporting)
  - transitive-reduction: no `requires` edge whose target is already an ancestor via another path
  - exactly one primary parent; structural nodes carry no `statement`/`requires`
- Test fixtures: one clean mini-graph, plus one deliberately-broken fixture per rule.

**Deliverable**: `GraphCore` with full test coverage of the validator.
**Exit criterion**: every seeded violation is flagged with the offending ids in the diagnostic; the clean fixture passes; ancestor queries are O(answer), verified on a synthetic 10k-node chain without timeout.

## Phase 2 — Content pipeline + seed content

**Goal**: YAML in, validated `graph.json` + deterministic layout out; Appendix A exists as real content.

**Tasks**
- `ContentBuild` executable with subcommands:
  - `validate` — parse all `content/**.yaml` (Yams), run the Phase 1 validator, emit diagnostics with file/line context, non-zero exit on failure.
  - `build` — compile to a single `graph.json` (nodes, edges, derived indexes) consumed by the app.
  - `layout` — offline force-directed layout (Fruchterman–Reingold with Barnes–Hut approximation; `contains`-taxonomy gravity so branches cluster per §6.1), **seeded RNG**, coordinates written alongside `graph.json`.
- **Encode Appendix A as real YAML** in `content/` — it is simultaneously the seed content for the viewer and the integration fixture for the pipeline.
- Wire `validate` into CI; add an app build phase that runs `build` + `layout` and bundles the artifacts.

**Deliverable**: `swift run ContentBuild build` produces app-consumable artifacts from `content/`.
**Exit criterion**: Appendix A YAML validates and compiles; running `layout` twice on identical input yields byte-identical coordinates; CI fails on a deliberately broken content file.

## Phase 3 — Render spike (decision phase)

**Goal**: prove the renderer before building UI on it. This phase produces a *decision*, recorded in this file, not product code.

**Tasks**
- Synthetic generator: ~10k nodes / ~30k edges with taxonomy-like clustering.
- **Primary hypothesis**: Metal via `MTKView` in `NSViewRepresentable` — instanced quads for nodes, line primitives (or instanced segments) for edges, zoom/pan as a transform uniform, picking via CPU-side spatial hash (quadtree).
- **Fallback hypothesis**: SpriteKit, same scene. Build only if Metal misses criteria or costs explode.
- Measure honestly: frame time under continuous pan/zoom, first-paint time from cold launch, label rendering cost at overview LOD (§6.1's label rules affect this heavily — test with hub labels on).

**Deliverable**: throwaway spike target + a short decision note appended to this plan (chosen renderer, measured numbers, rejected option and why).
**Exit criterion (numeric, from §6.4)**: 60 fps sustained pan/zoom at 10k nodes / 30k edges; first paint < 1 s from launch; hit-testing under 1 ms. Whichever candidate meets these first, wins.

## Phase 4 — Viewer

**Goal**: the real graph view over real content — §6.1's overview experience, minus scores.

**Tasks**
- Replace the spike scene with production `GraphView` rendering `graph.json` + precomputed layout.
- LOD per §6.1: label visibility by `prominence` × zoom level; node size by prominence; `requires` vs `relates` visual distinction at mid zoom; progressive reveal on first load (hubs first).
- Interaction: smooth pan/zoom (trackpad + scroll), hover highlights direct prerequisites/dependents, click opens the node panel (title, kind badge, statement with math rendering, summary, prerequisite list as navigable links). Math rendering: evaluate `NSAttributedString`-based LaTeX-lite vs. bundling a math-layout approach during this phase — smallest thing that renders the seed content acceptably wins; revisit at content scale.
- Local relaxation only (optional polish): tiny neighborhood-level force nudges, never a full-graph simulation at runtime (§6.4).

**Deliverable**: browsable Appendix A subgraph in the app.
**Exit criterion**: all §6.1 zoom behaviors demonstrable on seed content; node panel shows every field of every node kind; cold launch to interactive < 1 s.

## Phase 5 — Scoring engine

**Goal**: §4 and §5.1 as a pure, replayable `GraphCore` module — no UI yet.

**Tasks**
- Evidence log: append-only JSONL per §3.2/§5.1 (`node/edge id, grade|confidence, source, timestamp`), stored in Application Support; reader/writer with corruption-tolerant parsing (skip bad lines, report).
- **FSRS**: first task is a survey — check for a maintained Swift FSRS implementation; if none is suitable, port the reference implementation. Either way, validate against test vectors taken from the FSRS reference repo, and record the algorithm version in the log header (§4.2 prescribes adopting the reference, not transcribing formulas).
- Scoring fold: evidence log → per-node/per-edge FSRS state; retrievability computed on read (§4.1) — no timers mutate state.
- Graph propagation (§4.3): explicit review on N emits damped implicit reviews (γᵈ, defaults γ = 0.5, D_max = 3, constants in one config struct) to `requires`-ancestors; implicit reviews never lower scores; explicitly-exercised nodes (§5.2) get full-strength implicit reviews. All propagation lands in the log with `source: implicit` — auditable, replayable.
- Frontier computation (§4.5): unlearned nodes whose prerequisites all exceed τ.

**Deliverable**: scoring module with the evidence log as its only input.
**Exit criterion**: FSRS matches reference test vectors; replaying the same log twice yields identical scores; propagation tests confirm damping, depth cap, and the never-lower rule; a property test confirms fold order-independence for same-timestamp events.

## Phase 6 — Score display + review loop

**Goal**: scores become visible and changeable — §4.5 in pixels.

**Tasks**
- Color ramp per §4.5: gray for unlearned, cold-to-warm retrievability gradient, frontier accent ring; edges blend endpoint colors, `relates` edges show their own score.
- Self-report flow ("I know this" with a confidence grade) writing `source: self-report` evidence — the placeholder review instrument until Phase 8's problems exist.
- Review surfacing: due-node list (FSRS scheduler read-out) in a sidebar; reviewing from it updates colors live.
- Node panel gains score, history sparkline, and next-due date.

**Deliverable**: the living map — knowledge state visible, reviewable, decaying.
**Exit criterion**: on a fixture user, frontier set matches hand-computed truth; a self-report on a deep node visibly boosts its ancestors (propagation observable in UI); relaunching the app reproduces identical colors (fold determinism through the UI path).

**Tasks**

## Phase 8 — Assessment

**Goal**: problems replace self-report as the evidence instrument (§5.2–§5.4).

**Tasks**
- Problem schema (`problems/`): statement, answer/rubric, `targets: [node id]`, `exercises: [node id]`; validated against the graph (no dangling ids) by `ContentBuild validate`.
- Grading flow: answering emits full-grade evidence for targets, full-strength implicit evidence for exercised nodes (§5.2).
- Adaptive placement (§5.3): claimed-frontier seeding, DAG probing (pass ⇒ raise ancestor priors, fail ⇒ probe prerequisites), low-confidence inferred evidence with faster decay, resumable sessions.
- Failure diagnosis (§5.4): on a miss, present the prerequisite chain for gap localization; evidence lands on the localized node only.
- Author a problem bank for the M2 single-variable-calculus content (parallel track, same review bar as content).

**Deliverable**: placement + problem-driven review over real content.
**Exit criterion**: on a seeded persona ("knows calc through derivatives"), placement converges to the expected knowledge boundary within a bounded number of probes; a failed FTC problem localizes to the seeded gap.

## Phase 11 — Subject paths

**Goal**: M7 — §6.5. The goal of a focus session may be a `branch` or `subbranch`, not only a node: "learn linear algebra", answered with an ordered path.

**Tasks**
- `GraphCore`: `contentDescendants` over the `contains` DAG; multi-source `requiresAncestors`; generalize `FocusPlan` from a goal node to a `FocusGoal` (node | subject), keeping the single-node case identical to Phase 7's.

**Deliverable**: "learn linear algebra" answered with a personalized, ordered path.
**Exit criterion**: for a branch with authored content, the path is a valid topological order over the branch's content nodes plus their unmet prerequisites, omits exactly the met ones, and names the steps that come from outside the branch; an outlined-but-unauthored subject yields an empty path the app describes rather than a failure.

## Phase 12 — The program

**Goal**: M8 — §6.6. An authored curriculum over a whole tree: the spine (ordered units), per-node lessons, and a reader. Ships first for the quant tree, whose 58-subbranch outline order is the spine.

## Decision log

Decisions made during implementation that deviate from, or resolve an option left open by, the plan above. Newest phase last.

### Phase 0

**D0.1 — No Xcode project; the app is a SwiftPM executable plus a bundling script.**
The plan's repo layout named an Xcode project at `App/MathTree`. That path is kept, but as a SwiftPM `executableTarget` (`path: "App/MathTree"`), with `Scripts/bundle-app.sh` assembling `build/MathTree.app` (binary + minimal `Info.plist` + ad-hoc signature) around the built binary. Rationale: no project generator is installed (`xcodegen`/`tuist` absent), and a hand-written `project.pbxproj` is fragile and would force CI onto `xcodebuild`. CI stays `swift build && swift test` plus one script. A bare SwiftPM SwiftUI executable needs `NSApplication.shared.setActivationPolicy(.regular)` in the app delegate or no window fronts — done in `MathTreeApp.swift`. Reversible: if an Xcode project is ever needed (entitlements, notarization, App Store), the sources move unchanged.

**D0.2 — Deployment target macOS 15.**
Per the plan's default ("one major version behind current macOS"): dev machine runs macOS 26, so `.macOS(.v15)`. Revisit only if a Phase 3/4 Metal or SwiftUI API forces newer.

**D0.3 — Metal shaders are compiled at runtime, not by SwiftPM.**
Probed empirically before Phase 3 depended on it: a `.metal` file placed in a SwiftPM Swift target is **silently ignored** — no `default.metallib` is produced, `Bundle.module` isn't even generated, and `makeDefaultLibrary()` returns nil. So shaders ship as a text resource and are compiled at launch with `MTLDevice.makeLibrary(source:options:)` (tens of milliseconds, comfortably inside §6.4's sub-second first-paint budget). If that cost ever matters, the escape hatch is a `xcrun metal`/`metallib` step in `bundle-app.sh`.

**D0.4 — App launch is verified by a `--smoke-test` flag, not by screen capture.**
`MathTree --smoke-test` prints the visible windows and exits non-zero if there are none. Screen recording is not available to CI runners or to headless tooling, and this makes "launches to its placeholder window" an actual assertion. Current output: `window: "Knowledge Tree" 1280x800`.

**D0.5 — CI is delivered but not demonstrated green.**
The repo has no remote and none was created (that is the user's call), so `.github/workflows/ci.yml` has never run on GitHub. Every step in it was run locally and passes. Phase 0's "CI is green" is therefore *pending a remote*, not met.

### Phase 1

**D1.1 — Ancestor sets are a query, not an index.**
Phase 1's task list names "ancestor sets" among the indexes `KnowledgeGraph` builds on load. Built eagerly they are O(n²): the phase's own exit criterion is a 10,000-node `requires` chain, where materialized ancestor sets are ~50M entries. So the cheap indexes are eager (children by parent, dependents by prerequisite, reverse `relates`) and `requiresAncestors(of:)` / `requiresDescendants(of:)` are per-query traversals doing O(answer) work. Measured on the 10k chain: construction 66 ms, deepest-node ancestor query 9 ms returning exactly 9,999 ids, depth-bounded (`D_max = 3`) query 13 µs. The depth-bounded variant is what Phase 5's propagation will actually use.

**D1.2 — No `missing-statement` rule.**
`statement` is optional in the §3.1 schema and design.md never states its presence as an invariant, so a rule would false-positive on legitimately terse content. Structural nodes *are* checked for the inverse (they must carry no `statement`/`requires`/`relates`).

### Phase 2

**D2.1 — Hand-rolled argument parsing.**
Ground rule 3 sanctions Yams for tooling and nothing else. Three subcommands and five flags do not justify pulling in swift-argument-parser, so `ContentBuild` parses `CommandLine.arguments` directly.

**D2.2 — `GraphCore.contentFormatVersion` became `ContentFormat.version`.**
A `public enum GraphCore` inside module `GraphCore` shadows the module name, which makes `GraphCore.Node` unresolvable from any target that also imports Yams — and Yams exports its own `Node`. Renaming the enum was the fix; qualifying at every use site would have spread the problem.

**D2.3 — Node ids `ftc-1`/`ftc-2` → `ftc-part-1`/`ftc-part-2`.**
design.md contradicts itself: §3.1's normative schema example uses `analysis.svc.ftc-part-2`, Appendix A's table uses `an.svc.ftc-2`. Ids are permanent (§3.1) so this had to be settled before content scale-up. The normative section wins; Appendix A self-describes as "Illustrative only".

**D2.4 — What makes the build byte-stable.**
Four things, each of which independently breaks the Phase 2 exit criterion if dropped: content files are walked in sorted path order; `JSONEncoder` uses `.sortedKeys` (`dependents` and `children` are dictionaries, and Swift's dictionary iteration order varies between runs); layout iterates a sorted node order and uses a seeded SplitMix64 rather than `SystemRandomNumberGenerator`, which cannot be seeded; coordinates are rounded to 4 decimals on the way out. No artifact carries a timestamp or build id. Verified: three consecutive `build` + `layout` runs produce identical SHA-1s.

**D2.5 — Layout tuning.**
Fruchterman–Reingold, Barnes–Hut repulsion (θ = 0.9), fixed 600 iterations (a convergence tolerance would make output depend on floating-point noise). Springs are weighted `contains` 2.0 > `requires` 1.0 > `relates` 0.4, and each node is pulled toward its root branch's centroid. Measured on a synthetic 10k-node / 30k-edge taxonomy-shaped graph: inter/intra-cluster distance ratio 2.9 with cluster gravity off, 5.9 at the default 0.05, 7.9 at 0.12. 0.05 is the default because higher values collapse branches into unreadable blobs. Layout of 10k nodes takes ~5 s — offline, so it doesn't touch §6.4's first-paint budget.
*Known limitation, deferred to Phase 9*: initial positions come from an index-order spiral, so inserting one node reshuffles every position downstream of it. That is fine while content is a fixed seed set, but it fights §6.4's "spatial memory becomes navigation" once M2 authoring starts adding nodes incrementally — the fix is to seed positions from a hash of the node id rather than its index, and it should land before the map is something a user has memorized.

**D2.7 — `Package.resolved` is tracked.**
Pinned rather than ignored: this package produces executables, and leaving Yams to re-resolve on each CI run would let the build drift to a newer 5.x than the one it was tested against, which cuts against ground rule 5.

**D2.6 — The CI gate is tested, not assumed.**
`Scripts/check-broken-content.sh` seeds six distinct violations (dangling requires, cycle, transitive-redundant edge, duplicate id, malformed id, structural node with prerequisites) one at a time into a copy of `content/` and asserts a non-zero exit for each, then confirms clean content still passes. GraphCore's tests cover the *rules*; this covers the *wiring*, which is what silently rots — a swallowed exit code makes CI green on broken content.

### Phase 3

**Hardware for every number below**: Apple M4 (10-core GPU, unified memory), macOS 26.5.1, Swift 6.3.3, `swift build -c release`. Real `MTKView` in a SwiftUI window; drawable **2880×1736 px** (1440×868 pt at backing scale 2), 120 Hz display. Synthetic graph: 10,000 nodes / 30,167 edges (9,985 `contains`, 18,182 `requires` of which 14.6 % cross-branch per §2.4, 2,000 `relates`), prominence 0/1/2 = 7215/2172/478, positioned by the Phase 2 layout. All figures were reproduced on a second independent run before being recorded here.

**D3.1 — Metal wins; SpriteKit was never built.**
All three numeric criteria pass at 10k/30k with large margins, so the plan's own rule ("build the fallback only if Metal misses criteria or costs explode") says stop. Overview zoom with hub labels on, measured **offscreen with frames strictly serialised** — no pipelining, no compositor, the pessimistic number: **1.69 ms GPU mean, 2.1–2.2 ms GPU p99, 2.94 ms whole-frame p99** against a 16.67 ms budget. Triple-buffered throughput 814 fps at p99; in a real window it sustained a flat 120 fps (the display is the limiter — `currentDrawable` blocked 8.13 ms of every 8.33 ms frame). CPU encode p99 **0.20 ms**: three draw calls, zero per-frame uploads. Mid zoom is the same story (2.8–2.9 ms GPU p99). **Criterion 1: PASS, ~5.7× headroom.**
Also rejected: `.line` primitives for edges (no width control, no Retina antialiasing — instanced quads cost the same and look right); a quadtree for picking (see D3.3); CPU frustum culling (GPU-clipped off-screen instances beat the bookkeeping at every scale tested, including 100k).

**D3.2 — First paint ~0.21 s; the cost that scales is JSON decode, not the GPU.**
Measured from the kernel's process start (`sysctl` `kinfo_proc`) to the first *completed* drawable: **median ≈ 212 ms over five launches (range 204–221)**. Breakdown at 10k: AppKit/dyld/SwiftUI bring-up 164–182 ms, `graph.json` decode 28 ms (3.7 MB), instance-buffer build 2.7 ms, label atlas 5.0 ms raster + 1.1 ms upload, id→index resolve 1.6 ms, shader compile 0.5 ms, GPU buffers 0.07 ms. **Criterion 3: PASS, ~4.5× margin.** Three things Phase 4 should carry:
- **Metal caches the runtime-compiled shader on its source text.** A genuine cold compile costs **66 ms** (first paint 271 ms) — still passing, which confirms D0.3 was a safe call. Only a user's first-ever launch pays it.
- **First paint tracks decode and nothing else meaningfully**: 28 / 95 / 339 ms of decode at 10k / 30k / 100k nodes → 204 / 294 / 729 ms total. Still inside 1 s at 100k, but decode is then 47 % of it. If content nears 30k nodes, replace `graph.json` with a binary or mmap-able artifact. This is the number Phase 9's "re-measure each time the graph doubles" gate should watch.
- The **first launch of a freshly linked binary** costs 1.9–4.3 s (code-signature validation and page-in), against ~46 ms of our own work. State the criterion as steady-state launch and keep `bundle-app.sh`'s ad-hoc signing.

**D3.3 — Hit testing is a non-issue: 125 ns worst case against a 1 ms budget.**
CPU uniform grid in CSR form (counting sort), cell size = the layout's ideal edge length; build 0.16 ms for 10k nodes. Over 32,768 randomised picks: **47 ns mean / 61 ns p99** at overview zoom, 54 ns in the densest cluster, **worst single call 125 ns** (375 ns at 100k). **Criterion 2: PASS, ~8,000× margin.** A quadtree would be over-engineering; the grid stays.

**D3.4 — Frame architecture Phase 4 inherits: three static buffers, one uniform, three draw calls, zero per-frame uploads.**
- Nodes: instanced quad (`triangleStrip`, 4 verts × N instances), circle from an SDF in the fragment shader, premultiplied blend. `NodeInstance` = 16 B (`float2 pos; float radiusPx; uint rgba8`).
- Edges: instanced quad expanded perpendicular in screen space in the vertex shader, endpoint colours interpolated, alpha falloff across the width. `EdgeInstance` = 24 B. Guard `normalize()` against zero-length edges.
- Labels: `LabelInstance` = 48 B sampling an R8 `texture2d_array` atlas.
- Pan/zoom is **one 40-byte uniform** (`setVertexBytes`), never a buffer rebuild. Radii are in points, multiplied by the backing scale once.
- **LOD is an instance-count prefix, not a rebuild.** Sort instances by tier once at load (branch → subbranch → prominence 2 → 1 → 0); a zoom level is then `drawPrimitives(instanceCount: prefix)`. This is why CPU encode stays flat at 0.13 ms while the scene changes.

**D3.5 — Label cost is real but small, and the binding constraint is atlas *memory*, not draw time.**
Marginal cost is **0.19–0.31 µs per visible label**, roughly flat in graph size (it scales with label count × label area, not node count). §6.1's designed overview LOD — branch + subbranch hubs + prominence-2, i.e. 613 labels at 10k — costs **+0.14 ms per frame, under 1 % of the budget.** The label risk Phase 3 flagged did not materialise. What bites is the atlas: 613 labels = 2 pages = 8 MB / 5 ms to rasterise, but 10,000 labels = 22 pages = **88 MB** / 69 ms and 30,000 = **276 MB**. So: rasterise the overview tier eagerly at load (it is on the first-paint path and costs 5 ms), build higher tiers lazily per zoom band, release pages on zoom-out. Core Text into a grayscale `CGContext`, shelf-packed, uploaded once — no text engine, no per-frame glyph work.

**D3.6 — Edges are the only thing that scales badly; the cliff is ~170–340k edges.**
By ablation at overview zoom (serialised offscreen): edges are **~92 % of the frame** at both 10k and 100k, scale linearly at **≈46–49 ns/edge**, and are nearly insensitive to width (an 8× width range moves the total 1.27×) — so the cost is per-primitive screen extent (tile binning for long thin diagonals), not fill rate, not draw calls. Nodes cost 0.51 ms at 10k and only 0.84 ms at 100k. Extrapolated, the serialised budget is reached near **340k edges**, with a 2× safety margin at **170k**. §7's own estimate (5,000–15,000 nodes ⇒ ~15–45k edges) sits comfortably inside, so no edge LOD is needed for the planned corpus. Scale points measured: 10k/30k → 2.94 ms p99, 814 fps; 30k/90k → 6.05 ms p99, 300 fps; 100k/302k → 19.77 ms p99, 69 fps (**fails 60 fps**). When it grows, cull **edges**, not nodes — and note that at 100k the overview is a saturated white blob, so **legibility fails before frame rate does**; the answer there is content-driven LOD (draw `contains` plus high-prominence `requires` only at overview), not a rendering trick.

**D3.7 — Two measurement traps, recorded so Phase 4 doesn't re-learn them.**
- **`CAMetalLayer.displaySyncEnabled = false` does not uncap an on-screen `MTKView`.** The property reads back `false`, yet `currentDrawable` still blocks ~8.13 ms at 120 Hz. Worse, on-screen `gpuEndTime − gpuStartTime` is inflated ~3× by drawable scheduling (5.1 ms on screen vs 1.55 ms offscreen for an identical frame). **Profile offscreen**; treat the on-screen run only as "does it hold the display's cadence".
- **Never put `--flag value` pairs on an AppKit command line.** AppKit parses leftover `-key value` tokens into `NSUserDefaults`, and `--first-paint --graph x.json` made SwiftUI never call `makeNSView` — the window silently never existed and the process hung. A single *trailing* boolean flag survives, which is why D0.4's `--smoke-test` works. Anything richer must use environment variables or `--key=value`.

**Deliverable**: a throwaway SwiftPM spike (synthetic generator, Metal renderer, Core Text atlas, spatial hash, self-measuring harness), deliberately **not** retained in the repo — Phase 3's product is this decision, and Phase 4 writes the real `GraphView` from D3.4/D3.5 rather than growing the spike.

### Phase 4

**D4.1 — Edges are three draw calls, not one; the invariant that mattered was zero per-frame uploads.**
D3.4 handed down "three static buffers, one uniform, three draw calls". The buffers and the uniform are exactly that, but edges are split into `contains` / `requires` / `relates` and drawn as three ranges, each carrying its own width, alpha, dash duty and arrowhead strength through a 40-byte `DrawParams` (`setVertexBytes`). §6.1's mid-zoom clause — `requires` distinguishable from `relates` — needs per-class style, and the 24-byte `EdgeInstance` has no bits left for it. A typical frame is 5 draw calls (3 edge classes + nodes + labels), 7 while hovering. What the spike actually measured (0.13–0.20 ms CPU encode) was the *absence of buffer rebuilds*, not the draw count; two extra `setVertexBytes` are noise against that.

**D4.2 — `NodeInstance` keeps its 16 bytes but spends 4 on `half2` instead of `float`.**
D3.4's layout was `float2 pos; float radiusPx; uint rgba8`. Radius became `half2 radii` = (radius at overview, radius at full detail), mixed in the vertex shader by a `bandT` uniform. Same 16 bytes, but LOD *morphs* continuously instead of snapping at band boundaries — which is what makes zooming read as one continuous map rather than three. Half precision on a value in 1.9–17.0 points is well under a pixel. The same trick gives each label a `fadeStart` so tiers emerge at their own zoom.

**D4.3 — LOD is a hard prefix *and* a cosmetic fade; only the prefix is load-bearing.**
Instances are tier-sorted once at load (branch → subbranch → prominence 2 → 1 → 0) and a zoom level is `drawPrimitives(instanceCount: prefix)`, exactly as D3.4 specified. The per-tier alpha fade happens *within* the drawn prefix, so it never costs an instance that would otherwise be skipped. Measured on seed content, label prefix **9 / 19 / 27** across the three bands — §6.1's rule asserted, not claimed. The node prefix is 27 at every band and stays flat until a tier's radius falls below 0.75 px; the mechanism is present so scaling is a constant change, not a rewrite.

**D4.4 — Arrowheads ride mid-edge (62 % along), not at the target endpoint.**
An endpoint arrowhead must be backed off by the target's radius, which varies with the zoom band and is not carried per edge instance — no room in 24 bytes and no cheap vertex-shader lookup. A marker at a fixed fraction of the edge needs only the endpoints, stays legible at every zoom, and reads as flow rather than as decoration on the node. Arrow alpha ramps 0 → 0.85 over `bandT` 0.18–0.38, so arrowheads are absent at overview and present from mid onward; `relates` gets the complementary treatment (dash duty 1.0 → 0.5 over the same ramp).

**D4.5 — Zoom bands are multiples of fit-to-view, not absolute scale.**
`bandT = clamp(log₂(scale / fitScale) / 3, 0, 1)`; overview below 1.6× fit, mid 1.6–4.0×, detail above 4.0×. Anchoring to fit means "overview" means *the whole map* whether the corpus is 27 nodes or 10,000 — a threshold in points-per-world-unit would silently become wrong the first time content doubled. Probe and snapshot cameras use ratios 1.0 / 2.5 / 4.5 with anchors derived from content (busiest subbranch, best-connected content node), so "at mid zoom" is a reproducible camera rather than a hard-coded id.

**D4.6 — The label atlas is eager for one tier and lazy for the rest, per D3.5.**
Branch + subbranch + prominence-2 rasterise in the renderer's initialiser (2.4 ms, 9 labels, 1 page on seed content) because they sit on the first-paint path. Prominence-1 and -0 rasterise the first time `bandT` crosses their fade threshold. The label buffer is allocated once at full capacity and written as tiers arrive — still a static buffer, growing at band crossings, never per frame. D3.5's memory numbers are what force this: 613 labels is 8 MB but 30,000 would be 276 MB.

**D4.7 — Demonstrability: `--probe` is a trailing boolean; everything richer is an environment variable.**
D3.7's trap is respected literally. `--probe` renders the real scene in the real window, prints a JSON report from the first *completed* drawable, and exits; a 12 s watchdog exits 2 with a readable message rather than hanging — the exact failure D3.7 recorded. Snapshots are entirely env-driven (`MATHTREE_SNAPSHOT`, `_ZOOM`, `_SIZE`, `_REVEAL`, `_HOVER`) and render **offscreen**, so they need no window server. Because input cannot be driven headlessly, the probe also asserts the two calculations that would otherwise be unverifiable claims: projecting every node to screen and picking it back (**27/27**) and cursor-anchored zoom drift (**0.000000 pt**).

**D4.8 — Colour carries taxonomy, not score.**
Phase 4 is "minus scores", so §4.5's retrievability ramp is absent entirely. Hue is assigned per branch by sorted branch id (curated palette first, golden angle beyond it) so colours survive rebuilds, with saturation and value stepped by tier. This makes `contains` clustering legible now and leaves §4.5 a clean slot in Phase 6: the ramp replaces the tier tone, the hue assignment stays.

**D4.9 — LaTeX-lite wins the math-rendering evaluation; no layout engine is bundled.**
The plan's rule was "smallest thing that renders the seed content acceptably wins", and the corpus does not need a box model: the only genuinely two-dimensional constructs across 22 statements are super/subscripts and fractions. Super/subscripts are baseline offset plus a 0.72ⁿ size ramp — exactly `NSAttributedString`'s expressive power; fractions linearise to `(a)/(b)` with parentheses dropped around a single atom, so the hardest case, `$f'(c) = \dfrac{f(b) - f(a)}{b - a}$`, sets as `f′(c) = (f(b) - f(a))/(b - a)`. Cost: ~970 lines, zero dependencies.
The parser is pure Foundation and yields **two read-outs of one parse**: styled runs for display, and a linearised plain text where a script group becomes Unicode (`∫ₐᵇ`, `∑ᵢ₌₁ⁿ`, `xᵢ₋₁`) when every character has a script form. The second read-out exists precisely because the panel cannot be screenshotted — it is how the corpus was reviewed and what the self-check asserts against (clean over all 76 title/statement/summary fields).
**Degradation is the design constraint, not an afterthought**: content will always outrun the macro table. An unknown macro renders its braced argument if it has one and its own name upright if not; an unterminated `$` renders the remainder as math. Never a dropped tail, never a raw backslash — verified by 8,000 fuzzed renders over truncated and mutated real statements. The honest revisit trigger is not content volume but the first authored statement needing *stacked* notation (matrices, continued fractions), at which point a layout pass, not a bigger table, is the fix.

**D4.10 — The panel was verified by rendering it, and that found a real defect.**
Compile-clean plus `#Preview`s was the ceiling the panel work could reach on its own: the panel is a SwiftUI overlay, so it never appears in the renderer's Metal snapshots, and screen capture is unavailable here. It was therefore rendered offscreen (`NSHostingView` + `cacheDisplay` into a bitmap; `ImageRenderer` was tried first and leaves `ScrollView` content **blank**, which would have produced a false pass) for three nodes chosen to cover the kinds: `ftc-part-2` (heavy math, the only `relates` edge), `analysis` (structural), `def-riemann-integral` (the combining-mark worst case). Result: every §3.1 field renders, structural nodes correctly omit Statement/Requires/Related and gain Contains, and the math sets correctly — **except that the combining low line does not render on `∫`**. `\overline` joins (`∫̅ₐᵇ` is visibly barred), `\underline` does not, so `def-riemann-integral`'s lower integral displays as a plain `∫`. The statement stays unambiguous because `sup_P L(f,P)` and `inf_P U(f,P)` sit right beside it, but the notation is degraded. Fixing it needs a real overline/underline rule drawn as geometry rather than a combining character — which is the layout pass D4.9 defers, so it waits for the same trigger.

**D4.11 — Known gaps, stated rather than glossed.**
Three §6.1 behaviours are implemented but not *demonstrable* on 27 nodes: node-LOD culling never engages (nothing falls below 0.75 px), edge LOD does not exist by design (D3.6 put the cliff at ~170k edges against §7's ~45k estimate), and "branches read as galaxies" has only two branches to work with. Live trackpad feel is unverified — headless input is impossible here, so the probe asserts the underlying math instead. Local relaxation (listed as optional Phase 4 polish) is not built. The label atlas rasterises for `NSScreen.main` only, so a window dragged to a different-scale display resamples rather than re-rasterises.

### Phase 5

**D5.1 — Survey outcome: port, don't depend.**
Maintained Swift FSRS implementations do exist (`open-spaced-repetition/swift-fsrs`, MIT, FSRS-5 and -6). Ground rule 3 nonetheless rules them out: `GraphCore` takes **zero** third-party dependencies. So FSRS-6 is ported from the reference implementation, `open-spaced-repetition/py-fsrs` @ `8add2d3`. That commit is recorded in `FSRSVersion.oracle`, in the evidence-log header, and in the vector fixture — a test fails if they drift apart. swift-fsrs was also rejected as a *test* oracle: it may not carry py-fsrs's recent same-day-Hard stability fix, so a mismatch would be noise rather than signal. One oracle, pinned.

**D5.2 — Only the memory model is ported; the card-state machine is not.**
The reference's Learning/Review/Relearning states with their learning steps are Anki scheduling UX. Verified before porting that all three states perform **byte-identical** memory updates — the three-way branch is on elapsed time (`< 1 day` → short-term stability, else the recall/forget path), not on card state. So the port covers initial state, difficulty update, stability update, retrievability, and the interval read-out, and nothing is lost. Confirmed empirically: driving the reference with `learning_steps=()` reproduces its own published `test_memo_state` vector (S = 53.626903 vs 53.62691, D = 6.357487 vs 6.3574867). Interval fuzzing is omitted outright — ground rule 5 requires determinism.

**D5.3 — Vectors were generated before the port was written.**
FSRS publishes no standalone test-vector artifact; its reference test suite is the closest thing, and it contains only two memory-state assertions. `Scripts/gen-fsrs-vectors.py` therefore drives the reference to produce **420 unit vectors** (per-function grids over initial stability/difficulty, retrievability, next difficulty, short-term stability, next stability across 320 D×S×R×grade combinations, and intervals) plus **42 review sequences / 248 steps**, asserting every *intermediate* state rather than only the last. Generating the fixture first matters: a fixture written after the port would encode the port's bugs. The two published reference vectors are additionally asserted directly. The tests were mutation-checked — perturbing one weight from 1.8722 to 1.8723 fails four of them, so they can actually fail.

**D5.4 — Whole-day truncation in the update path, continuous decay for display.**
The reference computes elapsed time as `(t2 - t1).days`, floored to whole days, in both the update path and its retrievability call. The port matches that exactly in `review(_:grade:at:)`; anything else silently diverges from the oracle by amounts too small to notice and too large to ignore. But §4.1 says the score "decays continuously", and a colour that only moved at midnight would visibly step — so `retrievability(of:at:)`, the display read-out, uses fractional days. Two functions, deliberately, with the divergence documented at both sites.

**D5.5 — Propagation is write-time expansion; the fold never generates events.**
§4.3's implicit reviews must land in the log with `source: implicit` so they are auditable and replayable. That forces the split: appending an explicit review also appends the implicit events it induces (`Propagation.expanded`), and the fold only ever *applies* what it is given. Had the fold derived propagation while the log also stored it, every replay would double-count. Refitting γ later is then a filter, not a rewrite: drop `source: implicit`, re-expand the explicit events under new constants. Each implicit event carries its own `origin`, `depth` and `weight`, so a replay reproduces the original damping even after γ changes.
Mechanism: `S_new = max(S_old, S_old + γᵈ·(S_explicit(g) − S_old))`. Difficulty is untouched — §4.3 speaks only of stability, and difficulty is a property of the material rather than of this retrieval. Failures propagate nothing (§4.3 makes a failed review a retest flag, not a penalty); `propagateOnFailure` exists to test the never-lower clamp, which is otherwise vacuous. Depth is shortest-path — `requiresAncestorsByDepth` is breadth-first, verified before relying on it, so a diamond damps by its short route.

**D5.6 — An implicit review resets the decay clock, and that is a guess.**
Exercising a prerequisite *is* a retrieval of it, so its retrievability should recover; damping then expresses that the strengthening is weaker than a direct review, not that the retrieval never happened. But this is exactly the kind of constant §11.3 flags as unfounded, so it is a flag (`implicitReviewsResetDecayClock`) in `ScoringConfig` beside γ, `D_max` and τ rather than an assumption baked into the maths.

**D5.7 — A real ordering bug, found by a test asserting documented intent.**
FSRS updates do not commute, so the fold sorts events by a total order over their content before applying — order-independence comes from sorting, not from the maths. The first implementation ordered same-instant events by `source.rawValue`, which puts `"implicit"` before `"test"` alphabetically: the exact opposite of the ordering the code's own comment claimed. A node both reviewed directly and boosted at the same instant would have had the boost applied first, letting the explicit review compound an inflated stability. Fixed with an explicit `foldRank` (direct evidence anchors, derived boosts land on top). Worth recording because the bug was invisible to every test that only checked determinism — two wrong-but-consistent orderings are still deterministic.

**D5.8 — Confidence-only evidence is reported, not guessed.**
§5.1 allows an event to carry `grade` *or* `confidence`; the fold consumes grades. Inferred-tier handling (low confidence, faster decay, §5.3) is Phase 8/10 work, so a confidence-only event is surfaced as a fold defect rather than silently interpreted as some default grade. Unknown ids get the same treatment — which is also Phase 10's "malformed and unknown-id events are rejected with diagnostics, never crash, never corrupt the log" criterion, satisfied early and for free.

### Phase 6

**D6.1 — §4.5's ramp overrides D4.8's guess, and the hubs had to be desaturated for it.**
D4.8 predicted "the ramp replaces the tier tone, the hue assignment stays". Half of that survives. §4.5 prescribes an *absolute* ramp — grey when unlearned, deep blue → teal → green by retrievability — which cannot coexist with a per-branch hue on the same node, and §6.1 says colour encodes score *throughout*. So the split is by **learnability**: content nodes take §4.5's ramp, structural hubs keep their branch hue because they are not learnable (§2.1) and are the map's navigational skeleton. Rendering it exposed the consequence D4.8 did not anticipate: Foundations' branch hue is 152°, inside the ramp's own arc, so the hub read as a mastered node. Structural saturation therefore drops from 0.34/0.48 to 0.12/0.18 — hubs are near-white with a cast of their branch, and the galaxies still read through size, halo and the `contains` filaments, which keep full hue. The rule that came out of it: **nothing outside the ramp may sit inside the ramp's arc**, which is also why the frontier accent is warm gold.

**D6.2 — Edges: `contains` keeps taxonomy, `requires` blends endpoint scores, `relates` shows its own.**
§6.1 asks for blended endpoint colours and §4.4 gives `relates` edges their own FSRS state. `contains` is left on the taxonomy palette because its parent is structural and has no score — colouring it by one endpoint would be inventing data. `requires` keeps Phase 4's directional weights (0.55 at the prerequisite, 1.0 at the dependent) so it still reads as flow rather than a symmetric link, with the endpoints' score colours substituted. A `relates` edge with state paints both ends its own colour; without state it falls back to the endpoint blend, so an unexercised connection still reads as belonging to two nodes. Edge colours are dimmed 14 % against their nodes — §6.1 wants hairlines, and a well-known neighbourhood at full edge brightness becomes a blob.

**D6.3 — Self-report is affirmative only; there is no "I don't know this".**
Three confidence levels (Shaky / Solid / Fluent) mapping to Hard / Good / Easy. `again` is deliberately unreachable, and the reason is structural rather than stylistic: the frontier is defined by the *absence* of FSRS state (§4.5), so a self-reported failure would write state onto an unlearned node and silently delete it from "what you could learn next" — the opposite of what the user meant. §4.3 already says a failure is a retest flag, not a penalty; giving that its own semantics is Phase 8's job, alongside the problems that can actually localise a failure (§5.4). The rule lives in `SelfReportConfidence` and is asserted, not merely enforced by which buttons were drawn.

**D6.4 — The sidebar's due list is the scheduler, not the threshold, and the two are allowed to disagree.**
`ReviewQueue` reads FSRS's own `nextDue`; `Frontier.due` (Phase 5) asks the different question of whether retrievability has fallen past τ. FSRS schedules against its desired retention (0.90) and τ is 0.85, so the lists differ at the margin by construction — the scheduler decides *when to review*, τ decides *what counts as mastered for the frontier*. Both are kept. Only nodes are queued: `relates` edges carry state (§4.4), but an edge review means a problem exercised the connection, and self-reporting one would be evidence about a question nobody was asked.

**D6.5 — Every review is an append plus a full refold, never an incremental update.**
`ScoreStore.record` appends `Propagation.expanded(...)` and then re-reads and re-folds the whole log. Two reasons, one correctness and one evidential. Correctness: appended events can share a timestamp with existing ones, and the fold's total order only holds over the whole log (D5.7) — folding a batch onto current state would apply it in arrival order. Evidential: it makes the UI path *literally* the replay path, so "relaunching reproduces identical colours" and "replaying the log reproduces identical scores" stop being two claims. It costs one fold of a small file per button press, which is invisible at any corpus this design admits.

**D6.6 — Verification needed an injectable clock; without it the exit criterion is unassertable.**
Retrievability decays continuously against the wall clock (§4.1), so two launches over the same log *should* differ, and "identical colours" has no meaning until the clock is pinned. `MATHTREE_NOW` pins it; `MATHTREE_EVIDENCE_LOG` redirects the log; both are environment variables, per D3.7. Runs with `--probe`, `--smoke-test`, `MATHTREE_SNAPSHOT` or `MATHTREE_PANEL_SHOT` are **read-only** by construction — a verification run that appended would corrupt the developer's own history *and* stop being repeatable, which are the two things it exists to protect. Confirmed: after the whole verification pass, `~/Library/Application Support/MathTree/` still does not exist.
`Scripts/check-score-determinism.sh` launches the app twice over `fixtures/fixture-user.jsonl` and diffs the probe's score read-out — **27/27 nodes byte-identical**, comparing the rgba8 words read back out of the buffer the GPU drew from, not a recomputation. It then launches once over the one-review-later log and *requires a difference*, because a check that cannot fail proves nothing: 8 nodes repaint, frontier 4 → 5, learned 10 → 16. It is deliberately not in CI — it needs a Metal device, and the existing smoke test passes even when the renderer fails to come up, so a green CI run would not mean what this script means.

**D6.7 — Colour changes rewrite words inside existing buffers; the decay tick is a minute.**
D3.4's invariant is zero *per-frame* uploads, and neither a review nor a decay tick is per-frame — this is the pattern the hover highlight has used since Phase 4. `applyScores` rewrites node `rgba`, both scored edge classes, and a frontier-ring buffer sized for every node (a fresh user's frontier can legitimately be most of the map). The tick is 60 s, far finer than a ramp whose units are days, and it is suppressed when the clock is pinned. The trap worth recording: the `MTKView` pauses itself once the reveal settles, so a colour write is invisible until something asks for a frame — every recompute ends in `requestRedraw`.

**D6.8 — The fixture user is code; the JSONL is its golden output.**
Propagation is a write-time expansion (D5.5), so a log must *contain* the implicit events it induced — and hand-typing those would encode a human's arithmetic instead of `Propagation`'s. So `FixtureUser` authors only the eleven explicit reviews and derives the log, with `fixtures/*.jsonl` a committed golden copy (`MATHTREE_UPDATE_FIXTURES=1 swift test` regenerates; a test fails when they drift). They are committed rather than generated on demand because the app reads them directly, and a fixture the app can only obtain by running a test is not a fixture the app can be launched against.
The fixture earns its keep by being *borderline*: the MVT sits at 0.838 against τ = 0.85, so the threshold is load-bearing rather than decorative — that single node is why `zero-deriv-const` is off the frontier, and a test lowers τ to 0.80 to show it is the only thing moving.

**D6.9 — The overlays were rendered offscreen again, and again it found real defects.**
D4.10's method (`NSHostingView` + `cacheDisplay`; `ImageRenderer` blanks `ScrollView` content and would pass falsely) was reused for the score section and the sidebar, and caught two things that compiled and previewed fine: positioned subviews inside the sparkline's `GeometryReader` claimed layout space past their frame, leaving a visible dead gap under the chart, and edge markers clipped at the bounds. Both are gone — the sparkline is now one `Canvas` with an inset plot. Unlike Phase 4, the harness is **kept** (`PanelShot`, `DEBUG`-only, env-gated): the overlays will keep growing through Phases 7 and 8, and it is ~120 lines against the alternative of re-deriving the method each time.
It also closes the one link no snapshot can reach. Input cannot be driven headlessly, so the button press itself is unverifiable — but `MATHTREE_PANEL_SHOT_REPORT` drives `ScoreStore.record` over a *copy* of the fixture log, and the resulting file is **byte-identical to `fixtures/fixture-user-reviewed.jsonl`**. The write path therefore produces exactly the log the tests assert on, and the colour it produced (`#8C919E57` → `#49F27CFF`, frontier 4 → 5) is the one the snapshot shows.

**D6.10 — What the first launch looks like, stated rather than softened.**
With no evidence log the map is entirely grey except the structural skeleton and **one** gold ring, on `foundations.real.sup-inf` — the single root of the `requires` DAG. That is §4.5 working exactly as specified, and it reads as an instruction ("start here") rather than as an empty state, so the ramp was not pre-emptively softened to make a fresh install look busier. It does mean the first-run map carries almost no colour information; §5.3's placement probe is the designed answer, and it is Phase 8 work.

**D6.11 — Known gaps.**
`relates` edges can never show their own score yet: nothing writes edge evidence, because §4.4 says an edge review happens when a *problem* exercises the connection (Phase 8) — the render path is built and exercised by construction, but unreachable from the UI. Live trackpad interaction with the sidebar is unverified for the same reason all Phase 4 input was. The decay tick repaints on a timer rather than on a display link, so a node crossing a ramp boundary can lag by up to a minute — invisible at day-scale stability, wrong if τ ever becomes an animation. The panel's history sparkline replays one node's events on demand; that is O(log) per panel open and will want a cache long before it wants a different algorithm.

### Phase 7

**D7.1 — The syllabus and its layout live in GraphCore, because the app target has no tests.**
`FocusPlan` owns everything the exit criterion quantifies over: the unmet set, its order, the met-boundary compression, and the left-to-right column/row layout. The app contributes point spacing, colour and interaction — nothing assertable. The load-bearing choice inside it: layering is longest-path over the **full** ancestor subgraph, met nodes included, and the syllabus is the unmet set sorted by (layer, id). Any directed path strictly increases the layer, so this stays a valid topological order even when one unmet node precedes another *only through met intermediates* — the case a layering over the pruned unmet subgraph silently gets wrong, and the case `unmetPrecedenceSurvivesAMetIntermediate` pins. "Met" is checked against `Frontier`'s exact notion (state exists ∧ retrievability strictly > τ, one shared clock) so the gold rings and the syllabus can never disagree at the margin — where the fixture deliberately parks the MVT (0.838 vs τ = 0.85, D6.8), which is why the fixture syllabus *containing* the MVT is the single strongest assertion in the phase.

**D7.2 — "Compressed" means: visible at the boundary, elided behind it, counted always.**
§6.2 says met prerequisites are compressed; the reading implemented is structural, not just visual. A met ancestor is displayed only where the unmet chain actually touches it — as a direct prerequisite of an unmet node or the goal — drawn small and dim *in its true topological position*; every met node behind that boundary is elided entirely, with the count shown ("4 earlier prerequisites you already know are not shown") so compression reads as compression rather than absence. Consequence, observed on the reviewed fixture: elision can disconnect the drawn subgraph (the decayed Riemann-sum fragment floats apart from the goal's own boundary), because the paths joining the fragments run entirely through elided met nodes. It reads acceptably — fragments stay row-aligned and the syllabus carries the order — so met-path routing is deferred until real content produces an illegible case.

**D7.3 — The transition is a camera flight under an overlay fade; 60 fps is asserted structurally, per D4.11.**
Entering focus flies the camera to the goal at detail zoom while the overlay fades in; leaving flies back to the camera captured at entry (captured once — refocusing deeper must not overwrite where "Full map" returns to). The flight interpolates scale in log space (zoom is perceptually multiplicative), eases with smoothstep, snaps to the exact target at completion, and is cancelled by any user gesture. Frame rate cannot be measured headlessly, so the claim is structural: the flight writes the same 40-byte uniform a settled frame writes — zero buffer traffic, so a transition frame costs what D3/D6 already measured — and the probe reports the on-demand plan cost (0.1–0.2 ms on seed content) and the flight's target camera. The trap re-learned: the `MTKView` pauses itself when settled, so `flyCamera` must kick `requestRedraw` or the flight never takes off.

**D7.4 — The probe's focus goal is the deepest-ancestry content node, not the detail anchor.**
D4.5's convention (content-derived, deterministic cameras) is kept but the derivation changed: the detail anchor is the *best-connected* node, and its plan over the fixture user is trivially met — it would demonstrate nothing. The node with the most transitive prerequisites (`u-sub` on seed content) is the most demanding goal the corpus offers, which is the case focus mode exists for. The probe re-derives both exit-criterion clauses independently of `FocusPlan`'s internals — transitive-precedence topological validity and omits-exactly-met recomputed straight from FSRS state — and reported true for all three fixture states (empty log, fixture user, reviewed).

**D7.5 — The focus overlay was rendered offscreen, and for the third time the method found real defects.**
D4.10/D6.9's harness (`NSHostingView` + `cacheDisplay`; PanelShot now also writes `focus-*.png`) caught two things that compiled and previewed clean: adjacent-column labels colliding ("Continuous on [a,b] ⇒ integrable" ran into "FTC, Part I" — layered layouts put nodes on the same row in adjacent columns *constantly*), and long titles overflowing their column. Fixed by wrapping labels within their column's width and alternating them above/below the node by column parity. The write path is closed the same way Phase 6 closed it: `MATHTREE_PANEL_SHOT_REPORT` drives the real `ScoreStore.record` over a copy of the fixture log, still byte-identical to `fixtures/fixture-user-reviewed.jsonl`, and the after-report focus shot shows the syllabus collapse 7 → 1 — §4.3's propagation expressed as compression.

**D7.6 — Known gaps.**
Elision-induced fragmenting (D7.2) awaits an illegible real case. A plan recompute after a review snaps the canvas rather than animating node motion — the enter/leave transitions are animated, in-place compression is not, and making it so means diffing plans, which nothing yet justifies. Escape is owner-priority (panel first, then focus) and navigation keys are suspended while focus covers the map; live trackpad feel of the flight is unverified for the reason every phase has recorded — input cannot be driven headlessly. The syllabus list reuses `NodeReferenceRow`, so an entry's subtitle says "ready to learn" only for frontier nodes; a mid-syllabus entry whose prerequisites are unmet correctly reads "unlearned", which is §4.5 speaking, not a bug.

### Phase 8

**D8.1 — M2 never ran as a separate track; the seed corpus *is* the single-variable-calculus content.**
Phase 8's task list says "author a problem bank for the M2 single-variable-calculus content", and §9 gates Phase 8 on M2. M2 was defined as a parallel authoring track that could start once Phase 2's tooling existed; it never did, because Appendix A — encoded whole in Phase 2 — already *is* limits → derivatives → Riemann integration → FTC, 22 content nodes deep. So the bank is authored against `content/`, and the gate is satisfied in substance rather than skipped. What is genuinely deferred is *volume*: 22 nodes is a curriculum-shaped subgraph, not a curriculum, and Phase 9 is where both the content and the bank scale. Stated here rather than left as a silent renumbering.

**D8.2 — Grading expands propagation jointly across targets, not once per target.**
§5.2 gives a problem *many* targets, and Phase 5's `Propagation.expanded` takes one event. Looping it per target and concatenating emits several implicit events for the same ancestor at the same instant — and `ScoreFold` applies each one, so the interpolation `S + w·(S_explicit − S)` compounds and stability overshoots what any single review could produce. `Grading.implicitEvents` therefore expands **once**, emitting one implicit event per non-target node carrying the *minimum* depth over all targets (shortest route wins, matching `Propagation`'s own breadth-first rule) and the nearest target as its `origin`. `multiTargetProblemsEmitOneImplicitEventPerAncestor` asserts the property *and* asserts that the naive expansion really would have duplicated — a test that only checked the good path would have passed against the bug.

**D8.3 — "Unlearned" now means *never successfully retrieved*, not *no state entry*.**
Phase 8 is the first thing that can write FSRS state onto a node the user has never learned: §5.4's diagnosis localizes a miss, and the `again` lands on the localized node whether or not it has history. Under §4.5's old reading ("unlearned = no state"), that would silently drop the node out of the frontier — at the exact moment it had been *proven* to be the thing to learn next. The alternatives were to not record the failure (losing ground truth, which §3.2 makes the whole design's foundation) or to accept the frontier hole; neither is acceptable, and neither is necessary. So `ScoreFold` tracks `ScoreState.learned` — nodes with at least one passing grade, explicit or implicit — and `Frontier`, `FocusPlan` and `ScoreRamp` read that instead of dictionary membership.
The two readings differ **only** on nodes with failures and no passes, which could not exist before this phase: `check-score-determinism.sh` still reports the same 27 colours and the same 4 → 5 frontier move, and the golden fixtures are unchanged. A failed-only node is therefore grey, on the frontier, *and* due in the scheduler — three read-outs agreeing that it is both unknown and asked about.
Verified on the **map**, not just in the model, because nothing else could: no fixture log contains a failed-only node, so the determinism script has none to compare, and `FailedOnlyNodeTests` asserts `ScoreRamp` in GraphCore rather than the buffer the GPU draws from. The `PanelShot` placement run produces six of them, and `--probe` over its log reports all six as `#8C919E57` — `ScoreRamp.unlearned` exactly — with frontier rings drawn. The number that makes the point is their **retrievability: 1.0**. FSRS was just told about them, so the decay clock has not started; under the old rule the map would have painted a node the user had *just been measured as not knowing* at full mastery green. Not deep blue — green. That is the defect this decision prevents, and it is now read back out of the instance buffer rather than argued for.

**D8.4 — The inferred tier is confidence-as-weight; no second decay model exists.**
§5.3 wants untested-but-inferred knowledge stored as low-confidence evidence that "decays faster until confirmed by a direct test". Rather than a decay multiplier or a provenance flag on `MemoryState`, placement's committed events ride Phase 5's implicit path with `confidence` as the weight. A weight below 1 yields a fraction of the stability a real review would grant, lower stability *is* steeper decay in FSRS, and a later `source: test` event takes the full FSRS branch and replaces it. Zero new state, and `inferredEvidenceDecaysFasterThanARealReview` pins that the retrievability curves actually separate rather than trusting the argument.
Two things distinguish these from §4.3's propagation events even though both carry `source: implicit`. They are **not** `D_max`-capped — §5.3 says a pass raises *all* ancestors, and truncating at three hops would leave the deep foundations of a claimed curriculum grey forever — and they carry a `confidence`, with `depth`/`weight` left nil to say so in the log. **That is the discriminator D5.5's refit filter must use**: "drop every `source: implicit` event and re-expand the explicit ones" would destroy these, because `Propagation.expand` cannot regenerate them. The rule is *drop implicit events that carry no `confidence`*.

**D8.5 — Placement belief is a replay of seed + answers over graph **and bank**.**
`PlacementSession` stores only the claimed frontier and the ordered answers; the belief is recomputed, never stored — the same discipline as D6.5's refold, for the same reason (a derived thing with two derivations can disagree with itself on resume). The bank is a parameter because the session records the node a probe was *chosen for* while `Grading.evidence` grades **every** target of the problem asked. Crediting only `answer.node` left the belief calling a node unknown that the evidence log had just recorded as learned — belief and map disagreeing, which is precisely what `committedInferredEvidenceReproducesThePersonaOnTheMap` exists to forbid. The seed persona never hit it (that probe is a miss), so it was found by reasoning rather than by a failing test; `aMultiTargetProbeCreditsEveryTargetItGraded` now covers it, and asserts the un-banked call still under-credits so the parameter is visibly load-bearing.
Probe selection is §5.3's "binary-search style" over a DAG: the unresolved node maximising `min(unresolved ancestors, unresolved descendants)`, ties to maximum uncertainty then to id. Every constant in `PlacementConfig` is a §11.3-class guess and is named as one.

**D8.6 — Diagnosis ranks by longest-path layer, deepest first — and a failing test is what found it.**
The first ranking was weakest-first with *nearest-the-target* breaking ties, which put the failed target itself at the head of its own diagnosis chain: the symptom offered before the cause, the exact misattribution §5.4 exists to prevent. Reversing the tie-break exposed the second half: hop distance is the wrong measure entirely. `sup-inf` and `completeness` both sit five hops below FTC Part II even though one requires the other, so a tie there could still offer the symptom first. The fix is **longest-path layering over the target's ancestor subgraph** — any directed `requires` path strictly increases the layer, so "A is a prerequisite of B" always implies `layer(A) < layer(B)`. Same construction and the same reasoning as `FocusPlan`'s (D7.1). The chain is deliberately *not* `D_max`-capped: damping bounds how far credit spreads, but a gap can sit anywhere.
This is also §4.3's other half made concrete. That section says a failure "propagates as a *flag for retesting*, not as a penalty" and never says what the flag is; Phase 6 left it open (D6.3). It is this chain — the set of nodes a miss puts back in question, presented for retest, with nothing written until one is chosen.

**D8.7 — Self-report survives, and the corpus self-check was extended to prove the bank renders.**
§5.4 says review happens via problems "*whenever possible*", which is a routing rule, not a replacement: a node the bank can ask about gets the problem sheet, everything else keeps Phase 6's three confidence levels, and the panel offers both. Self-report stays affirmative-only for D6.3's unchanged reason — but `missed` exists on a *problem*, because a missed problem is a measurement with somewhere to go.
The bank roughly doubled the corpus's LaTeX-bearing text (235 fields across statements, worked answers and every rubric criterion), none of it in any node. `MathText.Check` was extended over it and given a real entry point (`MATHTREE_MATH_CHECK=1`, env-driven per D3.7), now a CI step. It reports clean, and reading its linearised output found one genuine renderer defect: `2x\cos(x^2)` set as `2xcos(x²)` because an upright operator name only spaced itself on the right. TeX spaces a `\mathop` on both sides; the node corpus never happened to write an operator directly after an operand and the bank does. Fixed, and the fix was verified by diffing the whole 235-field report across the change — **one line moved**. `|` is excluded from the "ends with an operand" test on purpose: it opens a group as often as it closes one, and including it turned `|\sin x|` into `| sin x|`.

**D8.8 — The bank is an optional artifact; the session is a file that can be thrown away.**
`problems.json` is written by `build` even when empty, so a stale artifact can never answer "is there a bank?" wrongly, and `ProblemDocument.load` never throws — losing the bank must not cost the user the map, and self-report is the documented fallback. It decodes after the renderer is standing, because D3.2 makes decode the dominant launch term and nothing assessment-related is on the first-paint path.
`placement.json` holds only seed + answers. Every probe writes its own graded evidence to the log the moment it is answered — that is a real measurement and belongs there whether or not the questionnaire is ever finished — so deleting the session costs the user their place, never their knowledge. Evidence is appended *before* the answer is recorded, and `committedAt` is stamped *before* the inferred batch is appended: both asymmetries fail toward "measured but forgotten" rather than "double-counted". `MATHTREE_PLACEMENT` redirects it and the read-only guard covers it, exactly as D6.6 requires of the evidence log.

**D8.9 — The overlays were rendered offscreen for the fourth time, and for the fourth time it found real defects.**
D4.10/D6.9/D7.5's harness now also writes `problem-*.png` and `placement-*.png`. Three findings that compiled and previewed cleanly:
- **The placement summary was unreachable.** The card branched on `isActive`, which is false once a session is committed — so committing sent the user back to the claim screen, and the "Placed" state the branch was written for could never appear. It branches on `session != nil` now.
- **Both sheets were fixed-height.** A `ScrollView` is greedy vertically, so `ScrollView { … }.frame(maxHeight: 720)` is *always* 720 tall: a three-line problem got six hundred points of empty card under its buttons. `SheetCard` measures its content (`onGeometryChange`, macOS 15 = D0.2's target) and takes `min(content, limit)`.
- **"has a problem" on every diagnosis row.** True, and useless — coverage is total, so the badge said nothing on all sixteen rows. Replaced with a hover-revealed **"test it"** that opens that candidate's problem instead of asserting the gap, which is §5.4's own parenthetical ("or a follow-up micro-problem") finally implemented rather than merely indexed.
The write path is closed the way Phases 6 and 7 closed theirs: `PanelShot` drives a real `PlacementStore` over *copies* of the log and the session file, with a scripted solver answering from the fixture user's actual knowledge state. It reports `answered=9 known=10 unresolved=0 inferred=7 frontier=6` — the app's own placement loop, not a picture assembled for the shot.

**D8.10 — Exit criteria, and the numbers behind them.**
Both halves are asserted over real content and the real bank, against a persona written down as a knowledge *set* and checked to be downward-closed under `requires` before anything else runs.
- *"Placement converges to the expected knowledge boundary within a bounded number of probes"*: the "knows calc through derivatives" persona resolves all 22 content nodes in **8 probes**, and the bound is pinned at the measured value rather than a comfortable one, so a policy regression has to be looked at. The belief's `known` set equals the persona's exactly and its boundary equals a boundary recomputed independently from the persona. A second persona ("knows only the reals") converges somewhere else — a check that cannot fail proves nothing (D6.6).
- *"A failed FTC problem localizes to the seeded gap"*: with everything FTC Part II needs mastered except `def-antiderivative`, the chain offers that gap first, localizing writes **exactly one** `again` on it, every other node's stability is unchanged, the gap stays on the frontier and becomes due, and `FocusPlan`'s syllabus for FTC Part II is exactly `[def-antiderivative]`.
Coverage is asserted too: every one of the 22 content nodes is targeted by at least one problem, because placement can only *resolve* what the bank can ask about. `check-broken-content.sh` gained ten problem-bank cases (dangling target, structural target, duplicate id, malformed id, missing rubric, no targets, inverted `exercises`, target-also-exercised, non-edge `connects`, untagged endpoint) — D2.6's lesson is that the *wiring* rots, and the bank is gated by the same step as content.

**D8.11 — Known gaps.**
`PlacementStore.record` accepts an unlocalized miss and the belief then treats the probed node as the failure while the log stays silent — belief and map disagreeing, on a path `ProblemSheet` cannot currently reach (it opens the diagnosis chain and only calls back once a candidate is chosen) but the API can. Documented at the call site rather than closed, because closing it means deciding whether "I missed it and I don't know why" writes an `again` on the target, which is §5.4 read the other way and deserves a UI that can produce the state first.
The 32 problems are self-graded against a rubric; nothing machine-checks an answer, and nothing can, for free-response mathematics. `Problem.kind` says what the sheet shows, not what can be verified. A node whose only problem has been used up in a session can end a placement run unresolved rather than probed again — honest, reported in the summary, and the reason landmark nodes carry two problems. Live interaction with the sheet is unverified for the reason every phase since Phase 4 has recorded: input cannot be driven headlessly, so `startRevealed`/`startDiagnosing` exist purely so the revealed and diagnosing states can be *looked at*. The "test it" micro-problem hop drops the original miss without evidence, which is correct (nothing was localized) but means a user who probes and then abandons has answered two problems and recorded one. Placement's belief constants are unfitted guesses (§11.3), and unlike γ there is not yet a replayable corpus to fit them against — the session file makes that possible, and nothing uses it yet. Edge evidence (§4.4) is now writable but by exactly one problem in the bank, so the `relates` render path is exercised by a single case.

### Phase 9

**D9.0 — Phase 9's deliverable, "the complete map", is *not* delivered. What is delivered is the process, the tooling, the outline, and the first two batches through it.**
Stated first and plainly, because everything below reads differently if this is buried. §7 puts undergraduate mathematics at 5,000–15,000 nodes at this granularity; the corpus went from **22 content nodes to 322**, across **15 of the 82 outlined subbranches**. The exit criterion's three clauses hold *over what exists* — the full corpus validates clean, the viewer holds Phase 3's numbers with room to spare (D9.9), and the spot-check reviews found no invariant violations — but "the complete map" is a volume claim and the volume is not there. The map itself says so: 67 subbranches render as empty hubs, and `validate` prints `15/82 subbranches authored` on every run.
This is the same shape as D8.1 and is recorded for the same reason. What genuinely *is* finished is the part §7.1 says does not get delegated (the outline), the part it says is the product (the review discipline), and the machinery that makes the remainder mechanical rather than novel: an authoring contract, a per-subbranch draft-and-review pipeline, a serial integration pass, and two instruments — `lint` and `--baseline` — that exist specifically because a corpus this size stops being readable end to end. Adding the 67th subbranch is now the same work as adding the 16th.

**D9.1 — The canonical outline is the deliverable that makes the rest parallel, and it is the whole of §1.**
§7.1's step 1 is "fix the `branch`/`subbranch` skeleton by hand; this is small and load-bearing; it does not get delegated". It was authored here in one pass: **12 branches, 82 subbranches**, covering every bullet of §1. Twelve rather than the "~15" §7.1 estimates, because complex analysis, measure theory and Fourier analysis are subbranches of `analysis` rather than branches of their own — the layout clusters by branch (`Artifacts.clusters`), so a branch is a *visual* galaxy on the map first and a taxonomy node second, and splitting analysis into four would draw four galaxies where a reader expects one. The subbranch count lands inside §7.1's 80–120.
Every outlined subbranch gets its file immediately, holding only its `subbranch` node until it is authored. That is deliberate and it is why the outline is worth doing first: the map shows the shape of the whole curriculum from day one, and the remaining work is *on the map* as empty hubs rather than in a tracking document. `validate` prints `N/M subbranches authored`; `lint` names the empty ones.

**D9.2 — §7.1's human review became adversarial model review, and that substitution is stated rather than implied.**
§7.1 step 3 says nothing merges without human review, and that the review bar *is* the product. What ran here is one author and one independent reviewer per subbranch file, the reviewer prompted with the human half of `content/README.md`'s checklist — atomicity, edge direction, direct-prerequisites-only, and above all hypothesis completeness — and explicitly told not to spend effort on anything the validator already decides. It is not the same as a mathematician reading it, and the corpus is not claimed to have had one. It is also not nothing: the reviewers changed something in every file.

**D9.3 — Cross-file edges are a separate serial pass, because transitive reduction is a global property.**
Authors work one file at a time and in parallel, so no author can see a sibling file. Rather than have them guess at ids that do not exist yet, the contract forbids referencing anything outside the corpus manifest, and the wiring between newly authored files is a *separate* pass that runs alone, after the batch lands. This is not only about ids: an edge that is correct and irredundant inside one file can become transitively redundant the moment another file's edges join it, and redundancy is exactly the rule the validator rejects a build for. A parallel integration would have each agent computing reachability over a graph the others are still changing.

**D9.4 — Bank coverage moved from corpus-wide to per-subbranch, and is asserted in both directions.**
See `problems/README.md`. D8.10 asserted that *every* content node has a problem; Phase 9 multiplied the content without multiplying the bank, and that invariant then had two futures — block the content, or be deleted. Neither is right, because the invariant was never about the corpus: §5.3's placement needs the region it is probing to be askable end to end, and `Belief.unresolved` already exists to *report* what it could not settle rather than round it. So `placementReady` is a declared manifest of subbranches, and two tests hold it from both sides: every declared subbranch is covered end to end, and every fully covered subbranch is declared. A bank finished without being declared fails just as loudly as a declaration without a bank. The corpus-wide number is printed by `validate` on every run and pinned only against regression.

**D9.5 — The persona is now a frontier plus closure, and what is asserted about it changed accordingly.**
D8.10's persona was a hand-written set of nine ids, checked to be downward-closed under `requires`. Wiring foundations underneath analysis made "knows the derivative" entail some sixty further nodes — all genuinely known by anyone who knows the derivative, none of them interesting to read. The persona is now four frontier ids and a computed closure. That makes coherence true by construction instead of by assertion, so the coherence test can no longer fail; what replaces it is a check the hand-written list could not make at all — that the declared frontier is an **antichain**, no member implied by another. `adifferentPersonaConvergesSomewhereElse` still guards the whole suite against vacuity.

**D9.6 — `lint` is advisory by construction, and one of its rules was deleted after being measured.**
`ContentBuild lint` reports and exits 0; `--strict` is opt-in and CI does not use it. A heuristic that blocks a merge is a heuristic that gets worked around, and §2.2 says outright that atomicity "can't be fully automated". The rules are the failures that only appear once nobody reads the corpus end to end any more: the same concept authored twice under two branches (`duplicate-title`), a node nothing reaches and that reaches nothing (`isolated-node`), a subbranch outlined and forgotten (`empty-subbranch`), and a whole branch that landed without its integration pass (`unintegrated-branch`). Each is tested against the thing it describes *and* against the hand-reviewed seed subgraph, which must stay clean.
That is not a slogan here. A `conjunctive-title` rule — "a title joining two things is usually two nodes" — was written, passed its fixture test, and **deleted after the first real corpus measured it**: 38 hits, no true positives on reading. "Domain and range of a relation", "Upper and lower bounds in a poset", "Kernel and image of a homomorphism" are dual notions that are one piece of knowledge, and mathematical English names things in pairs constantly. Every tightening either kept the false positives or lost the case the rule was written for. It went, because a rule with no precision teaches an author to skim past the whole report — including the `duplicate-title` lines underneath it, which on the same run found three genuinely duplicated concepts (`counterexample` in both `logic` and `proof`, `partition` in both `sets` and `relations`, and an indexed-family pair the titles did not even match on). All three were merged; the "a family *is* a function" observation that the deleted node carried survives as a `relates` note, which is where a connection belongs (§2.3).
`missing-statement` is D1.2's rejected validator rule, revived at advisory severity. D1.2's reasoning — `statement` is optional in §3.1, so a *fatal* rule would false-positive on legitimately terse content — is exactly the argument for having it here instead.

**D9.7 — Diff-aware review compares two compiled graphs, not two git revisions.**
`validate`/`lint --baseline <graph.json>` reports what a change did to the *graph*: nodes added, removed and **changed** — the distinction git cannot draw, since a node's file can be untouched while a rename elsewhere changes what it means — and, separately counted, which of the new `requires` edges crossed a branch boundary, which is the integration step §7.1 step 4 and this phase both hang on. `lint --baseline` additionally scopes its hints to the nodes the change touched, so a review of one subbranch is not buried under the corpus's standing hints. A graph baseline rather than a git ref keeps `ContentBuild` free of a git dependency (ground rule 3) and works the same in CI, in a worktree, and against an artifact from a tag.

**D9.8 — The renderer grew with the corpus, for the fourth time, and the corpus found three defects in it.**
`MATHTREE_MATH_CHECK` over the grown corpus reports clean, and — as in D8.7 — the value was in *reading* the linearised output rather than in the pass:
- `$(A, \le)$`, the standard way of naming a poset and everywhere in the new order theory, set as `(A, ≤ )`, with a hole before the bracket. TeX's spacing table gives Rel–Close and Rel–Punct a width of zero, and Open–Rel likewise; the renderer spaced a relation on both sides unconditionally. Now it checks both neighbours, including the macro spellings (`\rangle`, a sized `\right)`).
- `a \equiv b \pmod{n}` set as `a ≡ b  (mod n)`. `\pmod` carries its own leading space and the authored one survived; `append`'s doubled-space guard could not see it, because that guard fires on a lone `" "` and this is a six-character string beginning with one.
- Operator names and symbols the new branches need were added ahead of the content rather than after it (`\nmid`, `\rtimes`, `\lhd`, `\preceq`, `\operatorname`-free `\Gal`/`\ord`/`\Var`, …). An author who reaches for a macro and finds nothing writes *around* it, and the work-around is what ends up in the corpus permanently.
The whole report was diffed across the change: **11 lines moved, all three of the above, nothing else.**
A fourth finding came from the batch that landed after: the check's own `stray brace` rule fired on `ℚ as a quotient of ℤ × (ℤ ∖ {0})`, a *title* — plain text, where a brace is a character and not a group. The rule now counts braces against the ones the source typed outside `$…$`, so it means what it says: braces the **renderer** produced. Final run: **clean over 1,329 fields**, up from 864 at the previous batch and ~235 at Phase 8.

Re-measured under D3.2's own conditions — release build, warm launch (the first launch of a freshly signed binary costs 492 ms; D3.2 records why), median of five `--probe` runs on the same M4 hardware. Corpus: **416 nodes (12 branches, 82 subbranches, 322 content), 591 `requires` edges, 17 `relates`**, against the seed's 27/30/1.

|---|---|---|---|
| first paint | — | **202 ms** median (187–225) | < 1 s — **PASS, ~5×** |
| `graph.json` decode | 0.87 ms | **3.63 ms** | D3.2's "number to watch" (28 ms at 10k) |

**What the numbers miss, and the render does not.** Nobody had looked at the map, so it was rendered at overview and looked at. §6.1's legibility goal **fails**, and the cause is specific: the overview LOD draws 133 labels — 12 branches, 82 subbranch hubs, 39 landmarks — but **67 of those 82 subbranches are outlined and empty**. That is a content-driven LOD rule of exactly the kind D3.6 named, and it wants deciding with the label tiers in front of you, not at the end of a scale-up. Phase 9's "layout quality tuning" task is therefore *measured and diagnosed*, not done.

**D9.10 — Known gaps.**
**Volume is the gap**, and it shows up as more than a count. Sixty-seven subbranches are empty, and their absence is visible inside the authored files: `algebra.groups` states things about $GL_n(\mathbb{R})$, matrix multiplication and the determinant, `groups.def-homomorphism` about $\exp$ and $\log$, `groups.ex-units-mod-n` about Euler's $\varphi$ — all vocabulary whose home subbranch is outlined and unwritten, so the edges cannot be authored and the statements carry the terms uncited. That is the strongest argument that the remaining subbranches are not optional garnish.
The **problem bank did not grow at all**: 32 problems, 22 of 322 content nodes, three placement-ready subbranches out of fifteen authored. The manifest tracks it and `validate` prints it.
**Two layering questions were found and deliberately left.** (i) An "ℤ is defined in `number-systems`" edge at the root of `number-theory.divisibility` makes four of that file's own induction edges transitively redundant, because ℤ is built from ℕ by recursion and so *every* number-systems node reaches `induction-principle`; the choice is between divisibility keeping its direct induction edges (what it does today) and re-rooting it on number-systems. (ii) `foundations.cardinality` genuinely uses `number-systems` material — `continuum-cardinality`'s injectivity step is exactly `q-dense` — but wiring it would braid the two subbranches in both directions. Both are design calls above an integration pass.
**Two theorems exist twice**: √2's irrationality and the infinitude of primes, in `foundations.proof` as instances of a technique and in `number-theory.divisibility` as results. They are linked by `relates` from the number-theory side, which makes the duplication visible and scored, but they are not merged — and `lint`'s `duplicate-title` cannot see them, because the two tellings are titled differently. A title-blind duplicate detector is the obvious next rule and is not written.
**Propagation now fills the review queue with foundations.** A damped implicit review on a node with no history grants a *fraction* of a first review's stability, so it comes due almost immediately; with foundations wired under analysis, one self-report on the MVT leaves nine logic and set-theory nodes owed. This is §4.3 working exactly as written and is startling as an interface — the scheduler is telling a user they owe reviews on material they have never opened. It is asserted rather than hidden (`theDueListIsTheSchedulerReadOut`).
**Placement got slower for a structural reason** (see `placementConvergesToTheSeededBoundary`): `nextProbe` weighs bisection over all unresolved nodes, and three hundred of those are now unaskable, so they steer a search they cannot answer. 8 probes became 11.
**The renderer keeps authored spaces inside sized delimiters** where TeX drops them: `$\min \left( S \setminus \dots \right)$` sets as `min ( S ∖ … )`. Two occurrences in 1,329 fields. The general fix is to ignore literal spaces in math mode, which is what TeX does and which the `\pmod` and operator-name paths currently rely on *not* happening — a change with a wider blast radius than the defect.

### Phase 10

**D10.1 — The transport is a watched drop-directory, and the deciding criterion was not on the plan's list.**
The plan left the mechanism open between an XPC service, a local socket and a watched directory, with the criteria "Shifu runs on the same machine, events are small and append-only". Those two settle it against a socket — nothing to route, no streaming or backpressure shape for a connection to earn its keep with — but the criterion that actually decides it is a third: **neither process needs the other to be running.** XPC and sockets both require both ends up at once; Shifu observes usage all day and the map is open for minutes of it, so a live channel would silently drop evidence exactly when the user is not looking at the map. A directory is a queue that survives both processes. It is also inspectable and testable headlessly, which is why `shifu-sim` needs no IPC to stand in for Shifu at all.

**D10.2 — The transport determines the source, and Shifu cannot grade.**
The wire format has no `source` field and no `grade` field, and both are *ignored with a note* rather than rejected, so an early producer sees the message instead of quietly getting what it asked for. Everything arriving through the directory is stamped `source: shifu` — the evidence tiers stop meaning anything the moment the least trustworthy channel can claim the most trustworthy label. And §8.2's contract is `{node ids, confidence, source, timestamp}`: `confidence` is the only strength dial, exactly as placement's inferred tier uses a neutral grade (D8.4), because an observation says *whether* the user seems to have the knowledge, never how fluently.

**D10.3 — Shifu evidence does not propagate to prerequisites, and §8.2 is the reason.**
§4.3's propagation is defined for a *graded review*; an observation has no grade. The tempting extension — watching someone apply the chain rule is evidence about limits too — is real, but it is **Shifu's** to make: §8.2 gives Shifu ownership of "inference-to-node mapping", and the contract already lets one observation name every node it exercised. Naming them is the supported way to say it. Expanding at intake instead would also have to invent a rule for combining γᵈ with `confidence`, and the children would come out both confidence-carrying (preserved by D5.5's refit filter) *and* machine-regenerable (re-expanded by it) — precisely the ambiguity D8.4's discriminator exists to remove. `shifuEvidenceSurvivesTheRefitFilter` pins the discriminator itself.

**D10.4 — The fold's inferred tier keys off `confidence`, not off source.**
`ScoreFold.apply` used to take the damped path when `source == .implicit`. It now takes it when the event is implicit *or carries a confidence*, which is what D8.4 actually meant by confidence-as-weight: a weight below 1 buys a fraction of the stability a real review would, and lower stability *is* steeper decay. Keying off the value rather than the label let Shifu observations ride the existing path with no second decay model and no per-source special case, and it is the reason Phase 10 added no scoring code at all. `EvidenceSource.isInferred` (implicit or shifu) remains, but only for *fold ordering* — a measurement in the same instant must anchor the state before an inference lands on top of it.

**D10.5 — An observation is atomic; a document is not.**
If any id in an observation is unknown, the whole observation is rejected rather than partially honoured: an observation naming three nodes is one claim about a moment of usage, and keeping two of them changes what it says. One bad observation never costs the good ones in the same document, though — the document is a batch, not a claim. Only the envelope (malformed JSON, wrong shape, unsupported `schema`) condemns everything, and an unknown `schema` is rejected *unread* rather than interpreted under a guess about what its fields mean.

**D10.6 — File, then append, then receipt.**
The other ordering (append first, move second) turns a crash in the window into a document ingested twice, and two identical observations at one instant compound the way D8.2 found multi-target grading compounding — silently, with nothing afterwards to notice it by. Filing first loses at most one document, which Shifu can re-emit and which is low-confidence evidence anyway. The **receipt is what keeps that loss from being silent**: a document sitting in `accepted/` with no `.receipt.txt` beside it is exactly an interrupted ingest, and the next drain reports it and refuses to re-read it. This is the one place Phase 10 fails toward "lost" rather than D8.8's "measured but forgotten", and the reason is that the two failure modes are not symmetric here — a lost observation is one sample from a stream that keeps producing, and a double-counted one is a permanently wrong number.

**D10.7 — Parsed by hand over `JSONSerialization`, because the diagnostics *are* the deliverable.**
The exit criterion is about rejection with diagnostics, and a `DecodingError` for a typo in the fourth event of a document says far less than ``event 3: `confidence` must lie in (0, 1], got 4.0``. Shifu is a separate program written by someone else whose only debugging channel is the receipt file. One trap this exposed: `is Bool` is the wrong test for "is this a boolean", because `JSONSerialization` hands back `NSNumber` and *every* `NSNumber` holding 0 or 1 casts to `Bool` — the obvious guard rejected `"confidence": 0` as "not a number", and written the other way round it would have let `true` through as 1.0, the strongest claim the contract can make, from a field that was not a number at all. `CFGetTypeID` is the only thing that actually separates them, and `aBooleanIsNotAConfidence` pins it.

**D10.8 — Verified on the map, because that is what "visible score changes" means in this repository.**
`Scripts/check-shifu-intake.sh` runs both doors — `ContentBuild shifu-sim` and the app's own launch-time drain — and reads the resulting colours back out of the buffer the GPU drew from with `--probe`, exactly as Phases 6 and 8 did. It also asserts the negatives that a passing fold test cannot: the three unusable canned documents are filed with receipts and contribute nothing, relaunching does not re-ingest, and a `--probe` run without `MATHTREE_INTAKE_DRAIN` leaves a pending document untouched — the read-only guard D6.6 requires of every write path, now covering a path that writes without any user action at all.

**D10.9 — Known gaps.**
The drop-directory is drained at launch and on activation, not watched: a document arriving while the window is already frontmost waits for the next activation. `FSEvents` is the obvious upgrade and was not built, because the queue is the point and a few minutes of latency on inferred-tier evidence changes no colour a user would notice. Nothing rate-limits a producer — a runaway Shifu could append a million events and the fold, which is O(log) per event but O(n) per *reload*, would slow the app down long before anything else complained; the log's own size is the real limit and §11.1's SQLite swap-in is where it gets addressed. There is no way to *withdraw* an observation: the log is append-only by design (§3.2) and a mistaken inference can only be overridden by a later, stronger measurement, never deleted. `confidence` is trusted as given — the contract has no calibration story, and a producer that emits 0.9 for everything gets 0.9 for everything. And the canned stream is the only integration test there will be until Shifu exists; `ShifuStreamFixtureTests` guards the one failure mode that can rot silently, which is a node id in the stream being renamed by a later authoring pass.

### Phase 11

**D11.1 — A subject goal is the same computation with a goal *set*, so it is the same type, not a parallel one.**
The tempting alternative was a `SubjectPlan` beside `FocusPlan`: a subject has no single destination, and the existing struct's `goal`, `goalIsMet` and `.goal` role are all written about one. But everything *after* "which nodes am I aiming at" is identical — layering, the frontier's notion of met, met-boundary compression, column compaction, barycentre rows — and duplicating it would have produced two implementations of the one thing Phase 7's exit criterion tests. So `targets` became a set, the goal node became the "distinguished destination, if any", and the node case is literally the subject case with a one-element target set. The regression evidence is that all 265 pre-existing tests passed **unchanged** after the generalization: `aNodeFocusIsASingletonTargetSet` now pins that reading directly.
The one asymmetry is deliberate and is the difference between the two questions. A node goal is an *arrival*: it is excluded from its own syllabus, and it gets the terminating `.goal` role. A subject's nodes are *steps*: they are in the path, and no node in a subject plan wears `.goal`. Asking "what do I need for the FTC" and being told "…and then, the FTC" is right; asking "take me through linear algebra" and being told 25 prerequisites but not the 25 nodes of linear algebra would be absurd.

**D11.2 — Membership follows the `contains` DAG, not the primary tree.**
`contentDescendants` descends `containedChildren`, so a node cross-listed under a subject via `also_under` is part of it. §2.3 says a secondary parent exists *because* the topic belongs to that subject too — generating functions are cross-listed under Probability precisely because you cannot claim to know Probability without them — and a membership rule that ignored `also_under` would make the cross-listing decorative. It costs nothing: the descent is visit-marked, so a node reachable both ways appears once, and it is a target of both subjects that claim it, which is the intended meaning.
Structural descendants are dropped rather than carried: they have no score (§2.1), so a subbranch in a target set would sit unmet in every path forever — the same defensive filter `Frontier` and `FocusPlan` already apply to ancestors.

**D11.3 — `(layer, id)` stays the order, and no teaching heuristic was added.**
The tie-break is alphabetical inside a longest-path layer, which at subject scale interleaves branches: the linear-algebra path opens with logic and set theory in id order, not in a lecturer's order. Grouping by subbranch, weighting by `prominence`, or chunking into modules were all considered and none was built. `(layer, id)` is deterministic, is a valid topological order, and is the definition Phase 7's exit criterion — and every fixture assertion under it — is written against; a nicer order is a tie-break refinement to make with review data in hand, not a subsystem to invent at the same time as the feature. What the ordering *does* guarantee is the property that makes the list a path rather than a checklist: the first entry has the least layer of anything unmet, so all its prerequisites are met and it is always on the frontier. `theFirstStepIsAlwaysOnTheFrontier` pins it.

**D11.4 — The mini-graph scrolls now, because the numbers say a fixed frame cannot hold a subject.**
Measured over the real corpus before any view code was written: a single-node focus on the FTC is 13 columns and 26 displayed nodes; `linear-algebra` is **23 columns / 50 nodes**, `analysis` 21 / 86, `foundations` 29 / 195 with a 22-deep column. At the existing 96-point minimum column spacing that is 2,200–2,800 points wide, against a window that is typically 1,100 — the old layout would simply have drawn the far end off-screen, silently, with the goal end (the linear algebra) the part that vanished. The canvas now grows past the frame and scrolls in both axes; when the plan fits, the content *is* the frame and nothing scrolls, so every existing focus view looks exactly as it did. This was a latent defect at Phase 9 scale already (the FTC plan overflows a 1,100-point window by ~200 points); a subject goal is what made it impossible to miss.

**D11.5 — Imported steps are named, in words, on the row.**
Half of "learn linear algebra" is foundations, and the honest thing is to say so rather than to hide the detour inside a numbered list where every row looks alike. Each step outside the subject carries its branch name; the header states the ratio outright ("24 of these 49 steps sit outside this subject"); the mini-graph dims them and says so in the legend. This is the one piece of the phase that is a product judgement rather than a computation, and it is made in the direction of stating the cost — a user who is told up front that linear algebra starts in propositional logic can decide to do it; one who discovers it at step 13 concludes the tool is broken.

**D11.6 — Verified by rendering, as every display phase here has been.**
`MATHTREE_PANEL_SHOT` gained `path-linear-algebra.png` and `path-analysis.png`, and the sidebar and node-panel shots were fixed to actually pass the new callbacks — a shot that renders the view without the feature is a false pass, which is exactly what the first run produced. Reading the images changed two things that the tests could not see: the sidebar's progress read-out wrapped to two lines on `Foundations` ("3 / 195 mastered" does not fit 268 points), and the structural node panel had no learn action at all in the shot because the harness passed `onFocus: nil`. Both are fixed and both are now in the rendered output.

**D11.7 — Known gaps.**
The sidebar lists **branches only**, not subbranches, and sits **below the due queue**: 82 subbranch offers would bury the review queue the sidebar is named for, twelve branch rows above it would push the first due node off a 720-point sidebar, and the panel already offers any subbranch you click. There is no way to *filter* a path — no "just the linear algebra, I'll take the foundations on faith" — and no way to mark an imported step as skipped; §2.3's AND semantics say a prerequisite is required, and §11.2's OR-prerequisites are the open question that would change that. Nothing persists which subject you were last learning: the path is recomputed from the log every time, which is correct but means the app has no notion of "the course I am on" to return you to — and since "Learn this" on a step *retargets* the focus (Phase 7's behaviour, unchanged), one click from inside a path replaces it, with only the full map to come back to. The whole-branch mini-graph is honest and dense — `foundations` is 195 nodes in a 29 × 22 grid — and while it scrolls rather than clips, D9.9's finding stands unchanged: legibility is the constraint here, not frame rate, and a subject path is one more place that wants the content-driven LOD rule D3.6 named. Progress is counted in **nodes**, unweighted: mastering 25 one-line definitions and mastering 25 landmark theorems read identically, and `prominence` is sitting right there unused.

### Turn 1

Turn 1 is not a numbered phase, so its decisions are numbered `DT1.x` — Phase 11 landed on `D11.x` first, and one identifier for two unrelated decisions is worse than an ugly prefix.

**DT1.1 — Hue is the branch, luminance is the score, and §4.5 is amended to say so.**
Phase 6 spent hue on retrievability (deep blue → teal → green) and left the branch hue to the structural hubs, which meant the two questions the overview exists to answer — *where in mathematics is this* and *how well do I know it* — competed for one channel. D6.1 had already noticed the collision from the other side: it desaturated the hubs because the Foundations hub at hue 152° was indistinguishable from a mastered node. The redesign separates them instead. A content node takes its branch's hue and moves only lightness and chroma with the score; a structural node takes a near-neutral and no score at all (§2.1 — it is not learnable). Two independent channels, so a fresh user sees the taxonomy and a placed one sees both at once.

The ramp had to move to **Oklch** for that to hold. In HSV a lightness walk at hue 58° (yellow) is far lighter than the same walk at 276° (violet), so an equally-known node in two branches would read as two different scores; in Oklch it does not. `OKLCH.swift` converts; nothing else in the app uses it.

`ScoreRamp` is deliberately **unchanged**. It owns §4.5's *model* colour, which is what `--probe` prints, what `Scripts/check-score-determinism.sh` diffs and what `ScoreDisplayTests` pins — none of which is about what is on screen. What moved is the display's input: `ScoreVisuals` now carries ramp *positions* rather than colours, which is exactly what lets one score snapshot paint either appearance without recomputing a score. Switching appearance is a buffer rewrite, never a fold.

**DT1.2 — Edges go monochrome, and §4.4 is better served by it.**
§6.1 said "edges inherit blended endpoint colors". Under DT1.1 that would put a third colour system on a canvas that already carries two, and the design's own note is explicit that the map should carry its colour through its nodes. So `contains` filaments take one dim tone and `requires`/`relates` take one lit tone, with Phase 4's directional weights kept as pure intensity — a filament is still bright at the hub and faded at the child, which is what makes branches read as galaxies. §4.4 ("edge scores render as the edge's color intensity") is *more* literally implemented than before: an exercised `relates` edge moves its alpha, which is what that sentence asks for and what a second hue system was obscuring.

Node radii come down to roughly half Phase 6's, and the hub halo is deleted. Both are the design's, and both are load-bearing rather than taste: at the old sizes the hue-per-branch fills merge into discs of colour and the `contains` filaments disappear under their own endpoints. The design document recreated Phase 6's sizes beside its own for exactly this comparison.

**DT1.3 — Two surfaces, and the deviations from the frames are all additive.**
Chrome is a rule-separated command line (wordmark, taxonomy breadcrumb, three read-outs), a review rail that is a *scrim* fading out over the map rather than a bordered panel, and one opaque detail column. Chips, cards, filled buttons, radii, shadows and the panel sparkline are gone; the one affordance shape left is a word with a rule under it.

Four things the frames do not draw are kept, and the reason in each case is that the frame's omission would cost a *capability*, not a decoration: **Scheduled** is the only place the app says when the next review is coming; **Diagnostics** is where D5.8's fold defects surface instead of a log nobody reads; **self-report** is the only instrument for a node the bank cannot ask about (§5.4's "whenever possible" cuts both ways, and D6.3 still governs its shape); and the panel's **details grid** is Phase 4's exit criterion — "every field of every node kind" — restyled, not removed. One thing the frames *do* draw is dropped: the mid-zoom "112 nodes in view" stat, because the renderer culls by LOD prefix rather than by frustum and cannot count it. A number the app cannot compute is worse than one fewer number.

`MATHTREE_THEME` pins the appearance process-wide rather than being a snapshot flag: `--probe` and `MATHTREE_PANEL_SHOT` need the same control, and a headless run has no system appearance to fall back on. Without it the theme follows `colorScheme`.

**DT1.4 — Focus mode's columns are the diagram.**
Phase 7 drew a node-link canvas beside a numbered syllabus, which said the same thing twice — the canvas's columns *were* the syllabus's order. Turn 1 draws `FocusPlan.columns` as columns and drops the canvas. What that gives up is which stage-*n* node feeds which stage-*n+1* node; the column order still carries the dependency by construction, and the panel still lists exact prerequisites, so the fact is available rather than illustrated. The design adds one distinction `FocusPlan` does not model: a stage of unmet nodes that have been learned once and slipped is labelled DECAYED rather than UNMET, which is a display read-out over §4.5's states, not a fifth role.

**DT1.5 — The label cull is part of the design, and it is solved over a ladder of zooms.**
The prototype's support code culls labels greedily — tier order, three candidate offsets, dropped if nothing clears — and its frames are legible because of it. Ported, with one change forced by the difference between a prototype and a map: the prototype had two fixed frames and the app zooms continuously. So `LabelCull` solves the same greedy placement at seven zoom ratios and gives each label the zoom at which it *first* fits, which the existing per-instance `fadeStart` already knows how to render. A label keeps its offset once it has one, so nothing jumps sides as the camera moves; a branch name is never dropped, because §6.1 puts hub labels at overview unconditionally. Deterministic by construction — fixed ladder, the scene's own tier-then-id order, the shipped layout — so ground rule 5 still holds. Box widths are estimated from the point size rather than measured through Core Text: the cost of being wrong is one label kept or dropped at the margin, and the alternative is a text engine on the first-paint path.

**DT1.6 — Fonts are asked for, not bundled.**
The design specifies IBM Plex Sans, IBM Plex Mono and Source Serif 4. None ship with macOS. `Typeface` resolves each by family name and falls back to SF Pro, SF Mono and New York, so the *roles* survive everywhere — a mono, wide-tracked, uppercase eyebrow reads as an eyebrow either way, and Ledger's serif/sans contrast holds with New York against SF Pro. If the Plex family is installed, the frames match the design document exactly. Bundling a megabyte of font binaries into a repository whose ground rules keep third-party dependencies out was the alternative.

**DT1.7 — Phase 11's subject path is the same view, so it is the same columns.**
Turn 1 and Phase 11 were written against the same file from opposite ends: Phase 11 generalized focus mode's *goal* to a `FocusGoal` and grew the node-link canvas a scroll view to fit a 23-column subject path (D11.4); Turn 1 deleted that canvas. Merging them kept Phase 11's semantics whole and re-drew them in the column view — `FocusGoal` on the view, "LEARNING PATH" against "PREREQUISITE PATH" on the eyebrow, D11.5's imported steps set quiet with their origin branch named on the row, and the two empty states (outlined-but-unwritten, all-mastered) as words instead of a blank column. D11.4's measurement survives its implementation: the columns scroll horizontally for exactly the reason the canvas needed to, and a subject is what makes it unmissable.

One read-out changes shape with the mode rather than being computed twice. A node focus counts progress over the plan's own nodes — displayed plus elided, which is "how far along this chain am I". A subject counts `metTargets / targets`, because "37 of 50 nodes of linear algebra" is §6.5's headline and the prerequisites imported from Foundations are not part of the subject the user asked for. Same bar, different denominator, and the denominator is the honest one in each case.

**DT1.8 — Known gaps.**
The live appearance *switch* — `GraphRenderer.setTheme`, which rewrites colour words in place and re-rasterises the atlas because the two directions disagree about the tier-1 face — has never executed in verification: every capture pinned `MATHTREE_THEME` at launch, and there is no headless way to drive a system-appearance change here. `Scripts/check-score-determinism.sh` could not be run either: `--probe` needs a window server this environment does not have, and it fails identically on the pre-turn-1 build ("probe: no frame completed within 12s"), so this is environmental rather than a regression. The label cull's nominal viewport is 1280×800 — a much wider window shows the same labels, further apart, rather than more of them. And the mid-zoom legends key off the zoom band rather than off whether a highlight is actually on screen, so they appear on any mid-zoom frame, hovered or not.

### Phase 12

**D12.1 — The spine is authored data, and the validator turns its one convention into a precondition.**
The teaching order is not computable: `requires` yields a partial order with astronomically many linear extensions, and which one teaches well is pedagogy. So the spine is authored (`program.yaml`, the outline's §1–§58 verbatim — `theSpineFollowsTheOutlineOrder` pins the equality), and `program-order-violation` holds it to a **linear extension of cross-unit `requires`**. That rule is load-bearing, not hygiene: `ProgramPlan` orders each unit by its *own* edges only, which is complete precisely because precedence can never arrive from a later unit. The corpus's spine contract ("reference only earlier-ordered spines") made this true by construction; the validator is what keeps it true when someone reorders the spine without re-reading a contract.

**D12.2 — The bookmark is the first *never-learned* step, and decay deliberately does not move it.**
`FocusPlan` folds decay into the syllabus (§5.4 — a decayed prerequisite re-enters the path), and the program's *work* does the same: a decayed step is unmet, so adaptive mode un-compresses it. But `resume` reads `isLearned`, not met-under-τ, because a program position means "where I got to" — one decayed foundations node must not yank the bookmark from unit 40 back to unit 3. Decay reaches the user through the due list and the un-compression; `decayMakesAStepUnmetButDoesNotMoveTheBookmark` pins the split.

**D12.3 — Unit membership is the primary parent; §6.5's membership stays the `contains` DAG.**
D11.2 argued a cross-listed node belongs to *both* subjects, and it still does — a subject path is a claim about what you know. A program is a claim about where something is *taught*, and teaching a node twice because it is cross-listed would be the same lesson twice in one course. So `ProgramPlan` takes `children(of:)` (primary tree) where `FocusPlan.subject` takes `contentDescendants` (DAG), and `aCrossListedNodeIsTaughtOnlyInItsHomeUnit` pins the difference. Both readings are correct because they answer different questions.

**D12.4 — Lesson coverage is a per-file error and a corpus-wide report, split exactly as the bank split (D9.4).**
A corpus-wide coverage *error* would hold CI red from batch 1 until batch 58 landed. A per-file rule (`lesson-unit-incomplete`: a lessons file that exists must teach its whole unit, only its unit, exactly once) catches a generation batch's omissions at the batch boundary, and `validate` prints `lessons cover N/M content nodes (K/58 units complete)` on every run. Sections split by honesty rather than symmetry: `hook`/`explanation`/`recap` are validator-required, `worked`/`interview`/`pitfalls` are optional with lint hints (`lesson-missing-worked` on result/technique/example kinds, `thin-lesson`, `oversized-lesson`) — forcing a worked computation onto an `intuition` node manufactures filler, and filler is the opposite of the brief.

**D12.5 — One artifact, always written; the math check covers every lesson section and fails loud.**
`program.json` (spine + openings + lessons) follows `problems.json`'s rule: written even when empty, so a stale artifact can never answer "is there a program?" wrongly; `ProgramDocument` never throws and an unauthored program simply offers no surface. The corpus self-check gained `samples(for: Program)` — opening plus all six sections per lesson — because the lesson corpus is the largest LaTeX-bearing body in the repository once authored, none of it in any node or problem. An artifact that exists and cannot load exits 2 rather than noting and continuing, the same rule the quant graph got: a silently unchecked corpus is the outcome the check exists to prevent.

**D12.6 — Verified by rendering, like every display phase: `program.png`, and the frame is deliberately 3,800 points tall.**
`PanelShot` gained a program shot over a fixture program derived from the math tree's real taxonomy (82 units in the rail) plus one hand-authored chapter against real `analysis.svc` nodes. The height is the finding: the chapter scrolls, and an 800-point crop passed while showing *no authored lesson at all* — the lesson body, the one thing the phase adds visually, sat below the fold. The tall frame shows the contents rail with per-unit read-outs, the compression note, a DECAYED step in the attention colour, the missing-lesson state as words, and the full section rhythm (hook lead → explanation paragraphs → WORKED EXAMPLE → PITFALLS → RECAP) rendering correctly.

**D12.7 — The author's pre-flight check is Python, not Swift.**
Lesson generation fans out one agent per unit, and concurrent `swift run` invocations contend on `.build` locks — the one shared resource 58 otherwise-independent authors would have. `Scripts/check-lesson-file.py` mirrors the per-file validator rules plus the LaTeX allow-list with nothing but python3 + PyYAML, so an author validates *their one file* in isolation; `ContentBuild validate` remains the authority and runs between batches and in CI, and disagreements resolve in its favour.

**D12.8 — Known gaps.**
The reader's scroll-to-step works in the live app but not in the offscreen shot (`cacheDisplay` completes before the `ScrollViewReader` async scroll lands), so the shot verifies the chapter, not the jump. The adaptive/everything mode persists app-wide (`@AppStorage`), not per tree — acceptable while exactly one tree ships a program. Lessons carry no cross-references the app can follow (titles in prose, no links), and the reader offers self-report only — problems never route here, because the quant tree ships no bank; when one lands, the step foot should learn §5.4's routing rule. Unit openings are checked for presence, not read for quality, by anything but a reviewer.

## Risks (top three, with mitigations already embedded above)

1. **Renderer misses the numbers** — contained by Phase 3 being a cheap decision spike with a named fallback, before any UI is built on it.
2. **FSRS port correctness** — contained by reference test vectors and the versioned, replayable log (a wrong algorithm can be fixed and replayed, §3.2).
3. **Content authoring is the long pole** — contained by making it a parallel track from Phase 2 onward and gating only Phase 8 on it; engineering phases never wait on content beyond the seed subgraph.
